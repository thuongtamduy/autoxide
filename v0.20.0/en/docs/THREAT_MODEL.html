Autoxide documentation v0.20.0

Threat model of the core

Tiếng Việt: THREAT_MODEL.vi.md

What this is: the maintainers’ model of what an attacker could aim at in an Autoxide server, which controls exist today and what is still open. It was written with AI assistance from the code and the decision log, as input for a round of penetration testing by people outside the project. It is not an audit and does not claim that Autoxide is free of vulnerabilities. To report a problem, follow SECURITY.md.

  • Date: 2026-11-26, main of the 0.x series before 1.0
  • Roadmap item: step 71, G13 (docs/ROADMAP.md)
  • Builds on: the November 2026 review (code review and black-box test) and the November 2026 security and performance test (29,566 cases on both databases)
  • Method: STRIDE per trust boundary — Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege

How to read this document

Each of the eight boundaries below has the same parts:

  • Assets — what an attacker wants at that boundary.
  • Entry points — where data crosses it.
  • Trust assumptions — what the design takes for granted. A test that breaks an assumption is a finding.
  • STRIDE table — threat → existing control → residual risk or open item. A control names where it lives: a code path (relative to the repository root), a decision ID (D-… in docs/DECISIONS.md or docs/decisions/D-….md) or a gate rule of cargo xtask check. A control marked (to verify) is described by the design or the documentation but was not traced end to end in the code for this document; the list is at the end, in Controls to verify.

Findings of the earlier rounds keep their IDs: H-, M-, L-, I-, P- (review) and PT- (test).

Global assumptions

  • TLS is terminated by a reverse proxy or load balancer in front of the server; the server itself speaks HTTP (docs/DEPLOY.md). AUTOXIDE_HTTP_CLIENT_IP_HEADER / AUTOXIDE_HTTP_TRUSTED_PROXIES are set only when such a proxy exists (crates/kernel/src/config/http.rs).
  • AUTOXIDE_SECRET_KEY and AUTOXIDE_AUTH_TOKEN_SECRET are set to random values in production; the example values of .env.example are refused at startup (H-3; crates/kernel/src/security/secret.rs, modules/auth/src/config.rs).
  • The database and the file store are reachable only by the server and the operator.
  • The code is memory-safe Rust: unsafe_code = "forbid" for every workspace crate (Cargo.toml); release builds keep overflow checks (an overflow is a 500, not a wrap — PT-5).

1. Client ↔ HTTP layer

Assets: availability of the API; the mapping request → tenant; credentials in transit; tenant data in responses; browser sessions of tenants’ websites.

Entry points: every REST route under /api/v1/ (docs/openapi.json, about 1,300 operations); public routes (security((), ("bearer" = []))); /api/v1/openapi.json, /api/docs (opt-in), /llms.txt; /health/*; /metrics (opt-in); GET /api/v1/kernel/events/stream (SSE) and /events/ws (WebSocket); inbound provider webhooks (boundary 7); headers Host, Origin, Autoxide-Tenant, Authorization, Idempotency-Key, If-Match, the client-address header.

Trust assumptions:

  • The tenant of an authenticated request comes from the credential, never from Host or a header alone (crates/kernel/src/data/tenancy/request.rs).
  • A Host maps to a tenant only when that tenant has verified the domain by DNS TXT (crates/kernel/src/data/tenancy/domains.rs).
  • Public routes only return data the tenant has published; choosing another tenant for a public request (by host, header or ?site=) is allowed and exposes only that tenant’s public data.

2. API and MCP endpoint

Assets: the same data and actions as REST; the permission model; the parity promise “an MCP tool never does more than REST with the same permission” (CLAUDE.md rule 8).

Entry points: POST /mcp and /mcp/<module> (Streamable HTTP, JSON-RPC): tools/list, tools/call, resources/list|read, prompts/list|get, server/discover (crates/kernel/src/http/mcp.rs, http/mcp/protocol.rs, http/mcp/transport.rs; D-068, D-20261121-mcp-server). The manifest is docs/mcp-tools.json (about 310 tools).

Trust assumptions:

  • MCP is authenticated exactly like REST (Authorization: Bearer access token or API key), in a layer before the protocol code.
  • A tool handler is a thin adapter: it calls the same service function as the REST handler, and passes the Principal whenever REST limits that permission by scope.

3. Kernel

The kernel (crates/kernel) holds what every module relies on. The authentication module auth is a module, but its guarantees are kernel-level for this model, so it is covered here.

Assets: signing keys and sealed secrets; accounts, passwords, second factors, sessions, API keys; the permission catalog and role assignments; the organization tree; idempotency records; the outbox and the job queue; configuration.

Entry points: /api/v1/auth/* (sign-in, refresh, logout, MFA, passkeys, sign-in links, reset, invitations, OIDC, SCIM, API keys, roles, delegations, support grants); /api/v1/kernel/* (settings, tenants, domains, jobs, records, tags…); background jobs and the event dispatcher; process configuration.

Trust assumptions:

  • A business module checks permissions only through Principal (security/access/mod.rs) and never depends on auth (D-046).
  • Jobs and event handlers receive their tenant from the stored row, not from a request.
  • Configuration comes from the environment through ConfigReader; per-tenant settings go through the tenancy settings API.

4. Modules

Assets: each module’s tables and invariants (stock, money, publication state); the contracts between modules (traits in api, events); the public Rust API used by modules outside the repository.

Entry points: a module’s routes, tools, event subscriptions, jobs; context.require::<dyn Trait>(); Autoxide::new().module(…) for external modules (crates/app/src/lib.rs).

Trust assumptions:

  • Modules in this repository follow the boundary rules, enforced by cargo xtask check (D-031): a module exposes only pub mod api and pub fn module(…), does not import another module’s internals (module-import), does not query the database in handlers (handler-database), does not read the environment (env-access).
  • A module owns its tables (<module>_…), with no foreign key across modules and no join into another module’s tables (rules 1 and 4).
  • External modules are trusted code. They are compiled into the same process, with the same database connections and keys (D-20261121-external-modules). The repository’s gate rules do not run on code outside the repository.

5. Database

Assets: all data at rest; schema integrity; backups; the migration history; the audit chain.

Entry points: the server’s connections (read pool and write connection per database); autoxide migrate, autoxide backup, autoxide restore, autoxide copy (CLI on the server); scheduled backups to the file store; the tenant export job.

Trust assumptions:

  • Every feature runs on SQLite and PostgreSQL (CLAUDE.md “Luật số một”); a check that only holds on one database is a finding.
  • Every tenant-level table has tenant_id, and every query on it filters through .scoped(&tenant) (data/tenancy/scope.rs, D-253) — also when the tenant has its own database.
  • Only the operator can reach database files, credentials and backups.

6. Placement

Assets: which database and file store hold each tenant; placement connection URLs; domain → tenant mapping; data residency promises; tenants during a move, split or merge.

Entry points: autoxide tenant move and the platform-only REST / MCP endpoints for placements, moves and relocations (data/tenancy/placements.rs, moves*, relocate*; permissions kernel.placements.read, kernel.tenants.move, kernel.tenants.relocate); domain endpoints of each tenant (data/tenancy/domains*); sandboxes (data/tenancy/sandbox*).

Trust assumptions:

  • Only accounts of the platform tenant can move, split, merge or erase tenants (require_platform); a staff member who entered a tenant through support access cannot.
  • A tenant on its own database is still filtered by tenant_id (defence in depth).

7. External providers

Assets: money flows (payments, refunds, bank credits — the core never holds buyers’ money, D-187); shipment state; tax invoices; per-tenant provider credentials; outbound webhook secrets; the server’s network position (SSRF).

Entry points:

  • Inbound: /api/v1/ledger/webhooks/{provider}/{hook}, /api/v1/ledger/bank-feeds/{provider}/{hook}, /api/v1/shipping/webhooks/{carrier_code}/{hook}/{token} (and older forms); MoMo IPN, SePay bank feed, GHN status callbacks (modules/momo, modules/sepay, modules/ghn).
  • Outbound: payment, carrier, SMS (modules/esms), e-invoice (modules/einvoice_sepay) and mail calls; outbound webhooks (modules/webhooks, Standard Webhooks signatures, D-081); OIDC discovery; tenant SMTP; web push (WebPushSender contract).
  • Addresses chosen by users: webhook targets, OIDC issuers, SMTP hosts, push subscription endpoints, payment return_url, KYC return_url.

Trust assumptions:

  • Every provider account belongs to a tenant and is configured by that tenant; the server never falls back to another tenant’s account (crates/kernel/src/contracts/provider.rs, D-20261121-provider-accounts).
  • Provider connectors in this repository are experimental: written from public documentation, not yet run against the live services (header of each connector’s lib.rs).

8. AI

Assets: tenant content sent to a model; the operator’s model budget; integrity of what gets published; the instructions given to the model.

Entry points: features that call TextModel or Embedder (crates/kernel/src/contracts/ai.rs, published by modules/ai): SEO and alt-text suggestions, translations, product description drafts (catalog), support reply drafts (support/src/ai.rs), review summaries (orders/src/reviews.rs), conversation drafts, search by meaning. AI agents as API clients are covered by boundaries 1–3.

Trust assumptions:

  • AI is off until the installer configures a provider (docs/AI.md).
  • Model output is untrusted data: it must match a JSON Schema and only becomes a suggestion or draft; a person (or an agent with the publish permission) decides (D-109).
  • Rules for the model are in instructions; user data is only in input (Prompt::new(…).input(…)).

Out of scope

  • The operator: anyone with a shell, the environment, the database or the backups. Misconfigurations that SECURITY.md lists (CORS *, public /metrics, rate limits at 0, client-address header without a proxy, unset secrets).
  • Volumetric denial of service; cheap single-request amplification is in scope.
  • Administrators doing what administrators may do inside their own tenant.
  • User interfaces and SDK consumers (separate repositories), the reverse proxy, TLS configuration, the operating system, the container runtime, DNS of tenants’ domains.
  • Real provider accounts (payments, bank, SMS, carrier, e-invoice, identity) and AI providers; their own security.
  • Supply chain beyond what cargo deny, gitleaks, pinned actions and signed releases cover (docs/VERIFYING.md).
  • Legal compliance as such (see docs/COMPLIANCE.md); this model covers its technical controls only.

How to use this for the external test

Set-up. Use AUTOXIDE_TENANCY_MODE=multi, at least two tenants plus the platform tenant, an organization tree with unit-scoped staff, and both databases. The scripts of the November 2026 round (docs/security/pentest-2026-11/scripts/) build such a set-up and a case matrix; reuse them as a baseline rather than repeating the generated groups. Point every provider at a local fake or a sandbox account you own; test only your own installation.

Suggested focus, most value first:

  1. What the earlier rounds did not cover: passkeys and OIDC end to end in a browser; payment, bank-feed and carrier callbacks with real provider signatures (sandbox accounts); tenant move, split and merge between databases under load; tenants on their own database; file and media uploads at their size limits; WebSocket beyond the per-user cap; ai with a real model.
  2. Grant and scope logic (boundary 3): roles, memberships, delegations, support grants, SCIM, API key scope ∩ owner, automations’ run_as, step-up — look for any path where a principal ends up with more than its creator or holder. The P16 list names the areas known to be inconsistent.
  3. Tenant and branch isolation where the gate is blind (boundary 5): code paths the tenant-scope and mcp-principal rules do not see (generic queries, helpers, named handler functions) — compare MCP tools with their REST endpoints one by one.
  4. Host-based tenant resolution and CORS (boundary 1): verified domains, ?site=, domain changes between tenants, cache TTLs across several servers, suspended tenants.
  5. Money paths (boundaries 4, 7): currency and amount checks across every payment, refund, POS, stored-value and promotion path; races on both databases.
  6. AI drafts (boundary 8): whether injected content in reviews, tickets or product text can produce a draft that a client would render unsafely or that misleads a reviewer.
  7. Each control marked (to verify) below.

Reporting. Use the severity scale of the November 2026 review and the private channel in SECURITY.md. Name the boundary and STRIDE category from this document.

Controls to verify

Controls described by the design or documentation but not traced end to end in the code for this document:

  1. Every throttle and idempotency table has an expiry and a cleanup job (boundary 3).
  2. Every module that holds personal data registers it for export and deletion; nothing enforces it for new modules (boundary 4).
  3. A sandbox copies configuration only, for every module (boundary 6).
  4. Inbound provider callbacks: the replay / deduplication mechanism of each connector (boundary 7).
  5. AI drafts: output sanitising for every feature that stores model text (boundary 8).
