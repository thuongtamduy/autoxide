Autoxide documentation v0.20.0

Modules: what runs, and how to choose

Tiếng Việt

The Autoxide binary contains every module, but an installation only runs the modules it needs. One setting chooses them: AUTOXIDE_MODULES.

Three tiers

  • core — the server does not run without them (sign-in, idempotent writes, and what those need). Always on; they cannot be turned off.
  • official — on by default. Its API has no breaking change within one release line: a change that would break clients is made as a new endpoint, and the old one is declared deprecated with a removal date. A new release always reads the data of an older one (migrations run on their own). Security fixes reach every release line that is under long-term support.
  • experimental — off by default; turn one on by naming it. It works and is tested on SQLite and PostgreSQL like the rest, but its API may change between releases, breaking changes included; each change is listed in the changelog. The system never deletes its data on its own, but moving that data to a new release may need a manual step, described in the upgrade notes. An experimental module can be removed if nobody uses it, or become official.

A module is in one tier as a whole; tiers do not split a module. An official module never depends on an experimental one.

Becoming official: no open items left in the roadmap; real users; an API that did not have to change over several releases in a row; and, for a connector to an outside provider, a test run with a real account.

GET /api/v1/kernel/modules lists the modules that run on a server, with stability for each. In the OpenAPI document every operation of an experimental module carries "x-stability": "experimental" (an operation without it belongs to an official module), and docs/mcp-tools.json has stability for every tool; both also say so in the description.

Choosing: AUTOXIDE_MODULES

A comma-separated list. Each entry adds to the set; core modules are always in it.

EntryMeaning
coreOnly the core modules.
officialEvery core and official module. The default.
allEvery module, experimental ones included.
nameThat module, and the modules it needs.
-nameLeave that module out of the set chosen by the other entries.

Examples:

# The default, written out.
AUTOXIDE_MODULES=official

# Official modules plus two experimental ones.
AUTOXIDE_MODULES=official,bookings,support

# A website backend: sign-in, pages and posts, media, forms, menus. `media`, `files`, `ai`
# and `mail` come along because `content`, `forms` and `menus` need them.
AUTOXIDE_MODULES=content,forms,menus

# Everything official except plans and the commerce modules that are not needed here.
AUTOXIDE_MODULES=official,-plans,-customers,-orders

Mistakes are reported at startup, by every command, with what to write instead:

  • a name that is not a module lists the valid names;
  • -name for a module that an enabled module needs names the modules to leave out too (official,-catalog answers: leave out -inventory,-orders,-promotions as well, or remove -catalog);
  • -auth or another core module is refused.

autoxide doctor prints the modules that run and those that are turned off (the first line of autoxide serve’s log says the same), and autoxide config shows the value in use. autoxide modules lists every module of the program — also modules a binary of your own added — with its tier, whether it is on, what it depends on and, for a module that is off, whether the database still holds its data; autoxide modules --json prints the same for programs and agents.

Settings of a module that is turned off are not read: a leftover AUTOXIDE_NEWSLETTER_… line in .env is ignored. A task in AUTOXIDE_STARTUP_TASKS whose module is off is skipped with a warning in the log; a task name that does not exist in a module that is on is still an error.

What “turned off” means

A module that is turned off:

  • serves no routes: its paths answer 404;
  • is absent from the OpenAPI document served at /api/v1/openapi.json, from /llms.txt and from GET /api/v1/kernel/modules;
  • offers no MCP tools, resources or prompts;
  • runs no jobs and no schedules, and receives no events;
  • has no migrations applied: on a new database its tables are never created.

The files docs/openapi.json and docs/mcp-tools.json in the repository, and the SDKs built from them, always describe every module. autoxide openapi and autoxide mcp-manifest print that full contract whatever AUTOXIDE_MODULES says. A client can ask a server which modules it runs through GET /api/v1/kernel/modules.

Data of a module that is turned off

Turning a module off never deletes anything. If the database already has its tables, they stay, autoxide migrate up keeps applying the module’s new migrations to them, and turning the module on again continues from there.

While it is off, the module still takes part in personal data and in the tenant lifecycle (“dormant mode”) — it serves no routes, MCP tools, jobs or other events, but:

  • a person’s data export (GET /api/v1/auth/me/export, subject access requests) includes its part, and deleting an account deletes or anonymizes that person’s data in it, as when it is on;
  • deleting a tenant for good deletes its rows of the tenant (except tables kept by law), a tenant data export includes them, and moving, splitting or merging a tenant takes them along (the module’s own migrations are applied to its tables on both databases first, and only where it already has tables);
  • files still reads its own configuration while off and opens its storage, so deleting an account deletes the stored content too, and conversations deletes call recordings through that storage and the enabled voice connector; when the storage cannot be opened, the deletion is retried (nothing is reported done while content remains).

This is an obligation of personal data protection law (Vietnam: Law 91/2025/QH15, Decree 356/2025/ND-CP), so it does not depend on whether you use the module any more. What it still does not do while off:

  • retention clean-up of its data does not run (the module’s jobs do not run);
  • tenants created in the meantime do not get the module’s starting data;
  • events other modules publish in the meantime are not delivered to it later.

So that data is not lost by accident:

  • autoxide serve logs a warning at startup, and autoxide doctor reports modules_turned_off, when the database holds rows of a module that is off — with the exact AUTOXIDE_MODULES=… line that turns it back on. (When you set AUTOXIDE_MODULES yourself the message is informational: you chose.)
  • autoxide copy, autoxide backup and autoxide restore refuse to run while such data exists, because they only handle the modules that are on. Run them with the module turned on, or with AUTOXIDE_MODULES=all.

The check for such data looks at the main database and at the database of every placement.

To remove the data of a module for good, run autoxide migrate down <module> --steps 1000 — it works while the module is off (this drops its tables — back up first). autoxide migrate up keeps the tables of a turned-off module up to date where they exist, and never creates them elsewhere. migrate down has no --all: it acts on the main database only, so the module’s tables in the database of a placement stay (and migrate up --all keeps updating them) until you run it against that database too.

Upgrading from 0.17 or earlier

Up to 0.17 every module ran. From this release, with AUTOXIDE_MODULES not set, the eight experimental modules (bookings, newsletter, comments, support, conversations, analytics, reporting, automations) are off.

  1. Before updating, decide which of them you use. If unsure, update and run autoxide doctor: modules_turned_off lists the ones whose tables hold rows, and gives the line to add.
  2. Add that line to .env (or the environment of the container), for example AUTOXIDE_MODULES=official,newsletter,comments, and restart. To keep exactly the behavior of 0.17, use AUTOXIDE_MODULES=all.
  3. Roles keep the permissions of modules that are off, plans keep their features, and stored data stays; they take effect again when the module is turned on.

Nothing is deleted in either case, and the choice can be changed at any time.

For module authors

A module declares its tier and what it needs in its Module implementation; all three have defaults, so a module that declares nothing is official, optional and independent:

#![allow(unused)]
fn main() {
fn stability(&self) -> Stability { Stability::Experimental }
fn essential(&self) -> bool { false }
fn depends_on(&self) -> Vec<&'static str> { vec!["mail", "files"] }
}

List in depends_on every module whose contract you take with context.require::<…>()? in start. Contracts you take with .ok() are optional and stay out of it. A test in the binary starts each module with only the modules it declares, so a missing name fails the gate, not an installation. See MODULE_GUIDE.md for the rest of the contract.
