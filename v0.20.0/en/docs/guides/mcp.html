Autoxide documentation v0.20.0

Connecting an AI agent over MCP

Vietnamese: mcp.vi.md. Examples use curl with API set to your server (export API=https://api.example.com), and the TypeScript SDK (sdk/typescript). They run as tests against every build, so they match the server of this version.

AI agents call Autoxide as tools through the Model Context Protocol at /mcp (Streamable HTTP). Each tool runs the same code as the matching REST endpoint, with the same permission: a tool can never do what REST with the same permission cannot.

1. Create a key with the least permissions

Give the agent its own API key, with only what its job needs. content.write_own lets it write drafts of its own; publishing stays with people.

curl -sS "$API/api/v1/auth/login" \
  --json '{"email":"admin@example.com","password":"correct horse battery staple"}'
# save: TOKEN=.data.access_token
# save: REFRESH=.data.refresh_token

curl -sS "$API/api/v1/auth/api-keys" -H "Authorization: Bearer $TOKEN" \
  --json '{"name":"Writing agent","permissions":["content.read","content.write_own"],"current_password":"correct horse battery staple"}'
# expect: 201
# save: AGENT_KEY=.data.key

curl -sS "$API/api/v1/auth/me" -H "Authorization: Bearer $AGENT_KEY"

2. Connect the client

When the server has OAuth sign-in on, clients that support it (Claude, ChatGPT, Claude Code, IDEs) connect with the address alone and the person approves them in your interface: see Connecting MCP clients with OAuth sign-in. The rest of this section connects with an API key, which works with every client.

Claude Code:

claude mcp add --transport http autoxide https://api.example.com/mcp --header "Authorization: Bearer $AUTOXIDE_AGENT_KEY"

Other MCP clients take a Streamable HTTP server with a header, e.g.:

{
  "mcpServers": {
    "autoxide": {
      "type": "http",
      "url": "https://api.example.com/mcp",
      "headers": { "Authorization": "Bearer ${AUTOXIDE_AGENT_KEY}" }
    }
  }
}

An agent that works with one module only can connect to that module’s own endpoint, /mcp/<module> (for example https://api.example.com/mcp/content): same authentication and permissions, but only that module’s tools, resources and prompts, so the model does not have to read the descriptions of every tool on the server. /llms.txt links each module’s endpoint.

3. What the agent can do

tools/list shows only the tools the key’s permissions allow. Each description ends with the permission it needs, and annotations say whether a tool is read-only or destructive (clients ask before calling those). A deprecated tool says so in its description and in every result (_meta.autoxide/deprecation), with the tool to use instead.

Limits:

  • Requests with an API key share its rate limit (AUTOXIDE_HTTP_RATE_LIMIT_API_KEY_PER_MINUTE).
  • Every write lands in the audit log under the key.
  • AI results are suggestions and drafts that a person reviews; nothing an agent writes is published by itself.
  • Tool results have the same shape as REST: {"data": …}, or a page with pagination; errors carry the same code.

4. Resources and prompts

Besides tools, /mcp offers resources (read-only documents: resources/list, resources/read) and prompts (templates for common jobs: prompts/list, prompts/get). Both follow permissions like tools: a resource is listed only to callers with its permission, and a prompt only to callers who may call every tool it leads to. A resource or prompt the caller may not use answers exactly like one that does not exist.

Every signed-in caller can read autoxide://kernel/llms.txt (the same text as /llms.txt) and autoxide://kernel/openapi.json (the REST contract). Prompts never call anything by themselves: they return messages that tell the model which tools to call, and the user’s arguments come inside tags such as <topic>…</topic>, marked as data.

5. Let the agent find its way: /llms.txt

/llms.txt is a public page in the llmstxt.org format: where the OpenAPI document and /mcp are, how to authenticate, the conventions every endpoint follows, the installed modules and the MCP prompts and resources. It is generated from the code when the server starts, so it always matches this version. Links are absolute when AUTOXIDE_HTTP_PUBLIC_URL is set.

curl -sS "$API/llms.txt"

Under each module, /llms.txt links its own OpenAPI document and MCP endpoint and names its tools. A module’s OpenAPI document holds only the endpoints under /api/v1/<module> and the schemas they use, with the same conventions as the whole document — enough to call that module correctly without loading the rest of the API:

curl -sS "$API/api/v1/openapi/content.json"

6. From the quickstart to a working agent

A walk-through on your own machine, from an empty directory to an assistant that answers questions about stock and sales. It starts from the Quickstart (compose.quickstart.yml), so the server is at http://127.0.0.1:8080.

1. Sign in and make a key for the assistant. Use the administrator’s password from the file the server wrote (docker compose -f compose.quickstart.yml exec autoxide autoxide initial-password). Give the key only what the assistant needs — here, reading stock, products, prices and reports, and drafting invoices:

API=http://127.0.0.1:8080
TOKEN=$(curl -sS "$API/api/v1/auth/login" \
  --json '{"email":"admin@example.com","password":"<password from the log>"}' | jq -r .data.access_token)
curl -sS "$API/api/v1/auth/api-keys" -H "Authorization: Bearer $TOKEN" \
  --json '{"name":"Desk assistant","permissions":["inventory.read","catalog.products.read","catalog.prices.read","reporting.read","analytics.read","invoices.write"],"current_password":"<password from the log>"}' \
  | jq -r .data.key

The key (axk1_…) is shown once: keep it in your password manager. Check what it may do with curl -sS "$API/api/v1/auth/me" -H "Authorization: Bearer axk1_…".

2. Connect the client.

Claude Desktop takes local (stdio) servers in its configuration file (Settings → Developer → Edit Config, claude_desktop_config.json). The mcp-remote bridge (needs Node.js) connects it to an HTTP server with a header:

{
  "mcpServers": {
    "autoxide": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "http://127.0.0.1:8080/mcp", "--header", "Authorization:${AUTOXIDE_AUTH}"],
      "env": { "AUTOXIDE_AUTH": "Bearer axk1_…" }
    }
  }
}

Restart Claude Desktop; the tools appear under the tools icon of a new chat. (mcp-remote speaks plain HTTP only to localhost; a server elsewhere needs HTTPS.)

Cursor talks Streamable HTTP itself. In ~/.cursor/mcp.json (every project) or .cursor/mcp.json (one project — do not commit the key):

{
  "mcpServers": {
    "autoxide": {
      "url": "http://127.0.0.1:8080/mcp",
      "headers": { "Authorization": "Bearer ${env:AUTOXIDE_AGENT_KEY}" }
    }
  }
}

Start Cursor with AUTOXIDE_AGENT_KEY=axk1_… in its environment, then check Settings → MCP: autoxide should list its tools. For a narrower assistant, connect to one module only, e.g. http://127.0.0.1:8080/mcp/inventory.

3. Ask for real work. A fresh installation has no products or stock yet: add some first (the API reference at /api/docs after setting AUTOXIDE_HTTP_API_DOCS=true, or your own front end). Then ask in plain words; the model picks the tools, and the client shows each call before or after it runs.

You askTools the agent callsWhat you get
“Which products are running low? Group them by warehouse.”inventory.list_low_stock, then catalog.get_product for namesA list of variants under their reorder point, with the quantity on hand
“How many units of SKU TS-RED-M do we have, and where?”catalog.list_products (search), inventory.get_levelsStock per location: on hand, reserved, available
“Draft an invoice for Công ty ABC: 10 × TS-RED-M at the list price.”catalog.resolve_price, invoices.create_draftA draft invoice; a person reviews and issues it — the key has no permission to issue
“How did sales go last week compared with the week before?”reporting.summary, reporting.factsTotals and the change, from the reporting module’s facts
“Which pages brought the most visitors this month?”analytics.overview, analytics.top_pagesVisits and top pages of the website

What keeps this safe:

  • The key decides: tools/list shows only the tools its permissions allow, and a tool can never do more than REST with the same permission. The assistant above can read and draft; it cannot change stock, refund an order or issue an invoice.
  • Orders come from checkout, not from tools: there is no tool that places an order for a customer. An agent prepares drafts (invoices, content, replies) that people confirm.
  • Writes are safe to retry (idempotency) and every write is in the audit log under the key’s name (/api/v1/audit).
  • Remove the key when you are done: DELETE /api/v1/auth/api-keys/{id}.
