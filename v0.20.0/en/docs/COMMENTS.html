Autoxide documentation v0.20.0

Comments

Tiếng Việt: COMMENTS.vi.md

The comments module lets people comment on anything the website shows — a post, a page, a media item — by its kind and id (target_type, target_id). Threads have two levels: a top-level comment and its replies (a reply to a reply joins the same thread and remembers whom it answers). Signed-in users and guests can comment; every comment goes through a fixed chain of checks and, by default, guests wait for approval. People can report comments, moderators approve, reject, mark as spam, ban and close targets, and authors may change their comment for a short while and delete it at any time. It is API only: the website shows the comment box; the admin screens are a separate project. It lives under /api/v1/comments. The full contract is in openapi.json.

No third-party account is needed: spam is stopped by the core’s shared anti-spam layer (a hidden trap field, a signed form token, rate limits, duplicate detection; an optional self-hosted proof-of-work challenge) plus the module’s own word lists and link limit.

Permissions

PermissionAllows
comments.postCommenting while signed in, changing and deleting one’s own comments, one’s display name
comments.readReading every comment in any status, with author emails, network fingerprints and reports
comments.moderateApproving, rejecting, marking as spam, holding again; deleting for good
comments.manageBanning and unbanning; opening, closing and hiding targets
comments.exportExporting and erasing every comment written with an email address

Guests need none: everything under /api/v1/comments/public/ is open.

Targets

AUTOXIDE_COMMENTS_TARGET_TYPES (default content.entry) lists the kinds that take comments. When another module resolves a kind (the content module resolves content.entry), a comment is only taken when the target exists and is public; other kinds are taken as given. A target gets its row on its first comment, holding its state (open / closed, hidden, closes_at) and its counts. The module owning a kind declares which of its events close or remove a target: when content archives an entry its comments close; when it deletes one they are also hidden. AUTOXIDE_COMMENTS_AUTO_CLOSE_DAYS closes targets some days after their first comment.

Questions and answers

The same threads serve as product questions: a question is a top-level comment, answers are its replies. A module owning the target may give authors badges, computed when the comment is written and returned as stable codes in badges (e.g. seller for someone who manages the product, verified_buyer for someone who received it); show your own label for each code.

  • Search a target’s questions: GET /api/v1/comments/public/threads?target_type=…&target_id=…&q=bảo hành — ignores case and accents; matches with the exact accents come first.
  • Tab counts: GET /api/v1/comments/public/counts returns thread_count (shown questions) next to count (all shown comments); the target answers thread_count too, and moderators also get pending_thread_count.
  • Unanswered questions (no shown reply yet): GET /api/v1/comments?status=published&unanswered=true.
  • AUTOXIDE_COMMENTS_VERIFIED_ONLY_TYPES lists kinds where only verified accounts may ask or answer: guests are refused and signed-in users are checked with the module that keeps account verification (comments.verification_required, 403). With no such module installed, every signed-in account counts as verified.

Verified accounts (Vietnam, Decree 147/2024)

The compliance module keeps account verification and answers the question for this module:

  • Levels: none, phone (a Vietnamese mobile number confirmed with a 6-digit code sent by SMS) and identity (a verified identity profile, GET /api/v1/compliance/me/kyc; it includes phone). A user sees their level with GET /api/v1/compliance/me/verification (MCP compliance.account_verification).
  • Verifying a phone: POST /api/v1/compliance/me/phone-verifications {"phone": "0912 345 678"} sends the code (landlines and foreign numbers get compliance.phone_not_allowed), then POST /api/v1/compliance/me/phone-verifications/{id}/confirm {"code": "123456"}. A code works once, expires (AUTOXIDE_COMPLIANCE_OTP_TTL_SECONDS, 5 minutes) and allows a few wrong tries (AUTOXIDE_COMPLIANCE_OTP_MAX_ATTEMPTS); codes per number, account and address are limited. One number verifies one account unless the tenant raises the posting.max_accounts_per_phone policy (compliance.phone_in_use). DELETE /api/v1/compliance/me/phone removes the number. Sending needs an SMS provider; without one the server answers sms_disabled (503). No real SMS provider ships yet — install a connector module for yours.
  • How the two settings combine:
    • Kinds in AUTOXIDE_COMMENTS_VERIFIED_ONLY_TYPES need at least phone, or the level of the tenant’s posting.comments policy when that is higher (identity).
    • When the tenant sets posting.comments to phone or identity (PUT /api/v1/compliance/policies/posting.comments, permission compliance.policies.manage), every kind needs that level, and guests can no longer comment anywhere.
    • posting.comments = none (the default) leaves other kinds as they are.
    • A refused post answers comments.verification_required (403); send the user to verify, then post again.

The website

  1. GET /api/v1/comments/public/settings — limits and switches (guests allowed, edit minutes, maximum length, whether reply mails are on, whether Markdown is on).
  2. GET /api/v1/comments/public/threads?target_type=content.entry&target_id=…&order=desc&limit=20&replies_limit=3 — shown top-level comments with their first replies and reply_count; follow pagination.next_cursor. More replies: GET /api/v1/comments/public/comments/{id}/replies. Counts for a list page: GET /api/v1/comments/public/counts?target_type=content.entry&target_ids=a,b,c (up to 100). Whether the box is open: GET /api/v1/comments/public/targets/{type}/{id}.
  3. Show body_html (everything escaped, line breaks as <br>, http(s) addresses as links with rel="nofollow ugc noopener"); never insert body as HTML. Label guests as guests (author.kind). See “Text and Markdown” below.
  4. Each time the box is shown (never in cached HTML): GET /api/v1/antispam/token?scope=comments:content.entry. Show a hidden trap input that people leave empty.
  5. POST /api/v1/comments/public/comments:
{"target_type": "content.entry", "target_id": "0190…", "parent_id": null,
 "body": "Nice post!\nThanks.", "author_name": "Ada", "email": "ada@example.com",
 "notify_replies": true, "locale": "en", "form_token": "…", "trap": ""}
  • The answer is 201 with the comment, status (published, or pending: waiting for approval) and, for guests, an edit_token shown only here. A comment held for approval, held as spam or dropped by the anti-spam checks all answer pending: bots learn nothing.
  • Wrong input: 422 with every problem in errors (empty body, too long, reserved name, bad email…). A banned word: 422 comments.banned_word. A missing or expired token: 400 antispam.token_* — reload the form. A closed target: 409 comments.target_closed. A banned author: 403 comments.banned.
  • Sending the same form_token again returns the same comment (with a new edit_token; the first one stops working) and stores nothing new.
  • Signed-in users send their access token instead of a form token, need comments.post, and first choose a display name with PUT /api/v1/comments/profile {"display_name": "…"}.
  • Names (a guest’s author_name, a display name) take 1 to 50 characters, without control characters, invisible formatting characters (soft hyphen, direction marks, tag characters…), blank-looking letters (Hangul fillers and the like), or a word mixing Latin, Greek and Cyrillic letters (аdmin with a Cyrillic а). Letters that look alike across scripts in whole words (a name written entirely in Cyrillic) are not caught.
  • Change: PATCH /api/v1/comments/public/comments/{id} {"body": "…", "edit_token": "…"} within AUTOXIDE_COMMENTS_EDIT_MINUTES. The text is checked again, and the answer’s status says whether the comment is still shown: a shown comment waits for approval again when it now has suspect words or too many links, or when a new comment of the same author on that target would wait (mode pre, or first_time while the account has no shown comment) — so by default a guest’s change always waits for approval again. Delete: POST /api/v1/comments/public/comments/{id}/delete {"edit_token": "…"} (signed-in authors send {}) — text, name and email go, the place in the thread stays. An id that does not exist also answers 200, so a dropped comment cannot be told from a held one by deleting it. Changing one can: PATCH with the fake id of a dropped comment answers 404 comments.not_found (a known limit; it tells a bot only that this one comment was dropped).
  • Report: POST /api/v1/comments/public/comments/{id}/reports {"reason": "spam" | "abuse" | "illegal" | "other", "note": "…"}. Each account reports a comment once; guests are counted by network block (/24 for IPv4, /48 for IPv6).

Text and Markdown

A comment is sent with format: text (the default) or markdown, the latter only when GET /api/v1/comments/public/settings says markdown: true (AUTOXIDE_COMMENTS_MARKDOWN, on by default; when off, markdown is refused on the field format). An edit without format keeps the comment’s format. Old comments are text and show as before.

  • text: plain text. A * stays a *; line breaks are kept; http(s) addresses become links.
  • markdown: a small part of Markdown — **bold**, *italics*, [links](https://…) and <https://…>, > quotes, `code` and code blocks. Headings and list items show as paragraphs; images show as their text (no image is ever loaded); raw HTML shows as text. Only http(s) links work, all with rel="nofollow ugc noopener".

The server builds body_html from a fixed list of tags (p, br, strong, em, a, blockquote, code, pre), so the website inserts body_html as it is in either format. Markdown links count towards AUTOXIDE_COMMENTS_MAX_LINKS like bare addresses. Banned words are checked on the text as written.

Moderation

The checks run in this order: target closed → length → content (control and invisible characters refused) → duplicate → bans → banned words (refused) / suspect words (held) → too many links (held) → anti-spam → approval mode. Modes are pre (every comment waits), first_time (until the account has a comment that is shown now — one approved and later marked as spam or rejected does not count) and post (shown at once); defaults are pre for guests and first_time for users, and both can be set per target kind (AUTOXIDE_COMMENTS_MODERATION_BY_TYPE). A guest’s email is never proof of who they are — anyone can type any address — so it never lets a comment skip approval, even once confirmed.

  • GET /api/v1/comments?status=pending&target_type=&target_id=&q= — the queue (q searches text and names ignoring case and accents), with emails, network fingerprints, hold reasons and report counts. Each comment carries target_title and target_url when the target’s module can describe it and the target is public.
  • GET /api/v1/comments/targets?target_type=&state=open|closed&pending=true|false — the targets that have comments, newest first, with their counts and (when public) title and url.
  • PATCH /api/v1/comments/{id} {"status": "published" | "rejected" | "spam" | "pending"} with If-Match. DELETE /api/v1/comments/{id} deletes for good (a top-level comment with its thread).
  • Reaching AUTOXIDE_COMMENTS_REPORT_THRESHOLD reports holds a shown comment once; after a moderator approves it, more reports do not hide it. A comment held this way stays in the queue until a moderator decides: the cleanup never deletes a comment that was once shown. GET /api/v1/comments/{id}/reports.
  • POST /api/v1/comments/bans {"kind": "user" | "email" | "ip", "value": "…", "reason": "…", "until": null} (ip takes the comment’s ip_fingerprint), GET, DELETE /api/v1/comments/bans/{id}.
  • PUT /api/v1/comments/targets/{type}/{id} {"state": "closed", "hidden": false, "closes_at": null}.

Every decision is an event (comments.comment_status_changed, comments.comment_deleted, comments.ban_created, comments.target_closed…) that the audit module records with who and when.

Hidden by a case

A comment can be the target of a case of the compliance module (comments.comment:<id>; comments registers this type in the kernel’s resource directory, with the author as owner). When the case hides it (event compliance.target_restricted), the comment becomes rejected with hold reason compliance and remembers its former status; compliance.target_restored puts that status back. Meanwhile moderators cannot change its status (comments.restricted, 409). See COMPLIANCE.md.

Reply mails

Off until both AUTOXIDE_COMMENTS_VERIFY_URL and AUTOXIDE_COMMENTS_UNSUBSCRIBE_URL are set. With notify_replies: true and an email, a confirmation mail goes to that address (at most AUTOXIDE_COMMENTS_VERIFY_MAILS_PER_DAY); the website page sends its token to POST /api/v1/comments/public/verify. From then on, each shown reply to that comment mails the address with the target’s title and link — never the reply’s text or the replier’s name, so the feature cannot carry spam — and a link whose token goes to POST /api/v1/comments/public/unsubscribe ("all": true stops every comment followed with that address).

On a server with several tenants, a token may start with t<tenant id>.: it names the tenant itself, so the verify and unsubscribe calls work on any host of the API without the Autoxide-Tenant header. Send tokens back exactly as received (they may contain a .).

Personal data

  • GET /api/v1/comments/data?email=… lists, and DELETE /api/v1/comments/data?email=… clears, every comment written with an address (permission comments.export): text, name, email and network fingerprint go, the place in the thread stays, reply mails stop. Bans of the address are kept (they exist to keep it out); lift them by hand if asked.
  • Network addresses are never stored: only a keyed hash of the network block, cleared after AUTOXIDE_COMMENTS_IP_RETENTION_DAYS — from comments and from guests’ reports (the report stays, its reporter_key becomes expired:<report id>).
  • Comments waiting for approval or spam that were never shown are deleted AUTOXIDE_COMMENTS_RETENTION_DAYS after they were posted. A comment that was shown once and went back to waiting (held after reports, changed by its author, held again or marked as spam by a moderator) is never deleted on its own: a moderator approves, rejects or deletes it.
  • Events (and so webhooks) carry ids, targets and statuses only, never text, names or addresses.
  • When an account is deleted, its comments are cleared the same way, its display name is deleted and its reports no longer point to it. The account’s data export includes its comments, display name and reports.

Legal

What the law asks of comments depends on where you and your readers are. The module gives you settings, not rules written in the code; the texts below were not checked against the original legal texts — check them for your case before you rely on them.

  • Vietnam, Decree 147/2024/ND-CP (internet services): as read from secondary sources, social networks may only let accounts verified by a Vietnamese phone number comment; licensed general news sites may not be allowed reader comments at all; content that breaks the law must be taken down within 24 hours of a request from the authorities, and some services must keep moderation records (2 years is mentioned). The module offers AUTOXIDE_COMMENTS_ENABLED, AUTOXIDE_COMMENTS_ALLOW_GUESTS, AUTOXIDE_COMMENTS_SIGNED_IN_ONLY_TYPES, closing or hiding a target, deleting for good (DELETE /api/v1/comments/{id}, recorded with who and when in the audit log), and the illegal report reason. AUTOXIDE_COMMENTS_VERIFIED_ONLY_TYPES asks the module that keeps phone or identity verification (not this module) before taking a comment. How long the audit log is kept is set by the audit module.
  • Vietnam, Personal Data Protection Law 91/2025/QH15 and Decree 356/2025: people may ask for their data and its erasure; the module exports and clears by email and by account, keeps network data only as a hash and for a set time. Check the deadlines for answering requests, and whether keeping moderation records after an erasure (ids, actions and times only) is enough for you.
  • Elsewhere: for example the EU GDPR (data subject rights) and the Digital Services Act (notice and action for illegal content).

AI agents (MCP)

Tools comments.queue and comments.get (comments.read), comments.moderate (comments.moderate; pass the version you read, like If-Match) and comments.set_target_state (comments.manage), with the same permissions and checks as REST. For questions: comments.unanswered (comments.read) lists shown questions without a shown answer, and comments.answer (comments.post) answers one as the caller — like a signed-in user on the website, with the same badges, verification and moderation (set a display name first with PUT /api/v1/comments/profile). There is no tool to start a thread (that is for readers on the website) and no tool to delete a comment for good (use REST).

Per tenant

With several tenants, the settings above are the default of every tenant. A tenant can replace some of them with its own (its administrator with PUT /api/v1/kernel/settings/{name}, permission kernel.settings.manage; platform staff with PUT /api/v1/kernel/tenants/{id}/settings/{name}):

Tenant settingReplacesValue
comments.banned_wordsAUTOXIDE_COMMENTS_BANNED_WORDScomma-separated words; - for none
comments.suspect_wordsAUTOXIDE_COMMENTS_SUSPECT_WORDScomma-separated words; - for none
comments.max_linksAUTOXIDE_COMMENTS_MAX_LINKS0 to 100
comments.guest_moderationAUTOXIDE_COMMENTS_GUEST_MODERATIONpre, first_time or post
comments.user_moderationAUTOXIDE_COMMENTS_USER_MODERATIONpre, first_time or post

A wrong value is refused when it is set (422, the problem in errors). Overrides per target kind (AUTOXIDE_COMMENTS_MODERATION_BY_TYPE) still win over a tenant’s moderation mode. DELETE the setting to go back to the server’s value. GET /api/v1/comments/public/settings answers with the tenant’s own max_links.
