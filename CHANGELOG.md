# Changelog

Notable changes to Autoxide. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/spec/v2.0.0.html): while the version is `0.x`, a
minor release (`0.2.0`) may contain breaking changes, which are always listed under
**Changed** or **Removed**. The HTTP API itself never breaks within `/api/v1`: replaced
endpoints are marked deprecated with a sunset date first.

## [Unreleased]

## [0.20.0] - 2026-11-27

### Added

- Kernel `db` layer: `within(limit)` runs a read with a time limit, on a query built with `find` (with `all`,
  `one`, `count`, `exists`, `select` and `page`) or on hand-written SQL (`Sql::within`). The database stops the query when it runs past the limit or when
  the caller stops waiting (PostgreSQL `statement_timeout` and `pg_cancel_backend`, SQLite interrupt), and the read
  fails with `503 db.query_timeout` (`db::is_query_timeout`). Waiting for a pool connection counts toward the
  limit. `Database::read_pool_size()` gives the size of the read pool.
- `autoxide demo`: try Autoxide in one command, with no setup. It creates a folder, a SQLite database, random
  secrets and an administrator whose password is printed on screen, loads the reference data and serves the API
  with its reference page at `/api/docs`. Also `docker run --rm -it -p 127.0.0.1:8080:8080
  ghcr.io/thuongtamduy/autoxide:latest demo`. See `docs/GETTING-STARTED.md`.
- Release pages now carry binaries for macOS (arm64, x86_64) and Windows (x86_64) next to the Linux ones; they are
  not signed with an Apple or Microsoft certificate yet (`docs/GETTING-STARTED.md` says how to open them).
- `cargo xtask doctor` checks that a developer's machine has the tools the repository needs, with one install command
  for each missing one; every violation of `cargo xtask check` / `check-module` now prints a `how to fix:` line.
- A `.devcontainer/` for Codespaces and VS Code, an English `AGENTS.md` for people and agents outside the project,
  and rules for Cursor (`.cursor/rules`) and Copilot (`.github/copilot-instructions.md`).
- `autoxide demo` always uses its own SQLite file and ignores `DATABASE_URL` from the environment and `.env`, so it
  cannot touch a real database; `--database-url` points it at another database on purpose.
- `autoxide demo` also turns off outside services from the environment (SMTP, S3, OpenTelemetry, AI providers, provider
  modules), so a try-out never sends a real email or writes to a real bucket; `--keep-external-services` keeps them.
- `autoxide doctor` checks the tenant databases (`kernel.placements`): it names every one that is behind (its tenants
  get 503) or was left `migrating` by a process that stopped, and says how to fix it.
- The module repository generated by `cargo xtask new-module --external` now carries short rules for Cursor
  (`.cursor/rules/module.mdc`) and Copilot (`.github/copilot-instructions.md`) next to its `AGENTS.md`.
- New guide `docs/guides/rust-errors.md`: the seven Rust compiler errors people meet first when writing a module, with the
  real messages and the fix.
- Kernel: a database layer for modules, `autoxide_kernel::db`, so a module no longer depends on SeaORM. A table row is a
  `#[derive(Record)]` struct with typed columns (`Note::TITLE.eq(42)` does not compile), and `tenant.db()` filters every
  read, write, join and subquery by the tenant. An insert of another tenant's row is refused, and `ON CONFLICT DO UPDATE`
  never overwrites another tenant's row. The derive refuses, at compile time, a table that does not belong to the module.
  At startup the kernel checks each record a module declares (`Module::records`) against the live schema. The sample
  module `notes` uses it.
- Kernel: an HTTP layer for modules, `autoxide_kernel::http`, so a module no longer depends on axum, utoipa or
  validator. A handler takes `#[endpoint(…)]` (the grammar of `utoipa::path`) and must say who may call it:
  `permission = "…"`, `signed_in` or `public`, plus `approval = "agent"` for calls an AI agent must have
  approved. A missing declaration does not compile, and `x-permissions`, `x-public` and `x-approval` are generated, never
  written by hand. The standard 401 and 403
  responses, `operation_id` and the `ETag` header (`etag`) are filled in. `routes![…]` builds the module's routes for the
  new `Module::endpoints`. Types use `#[derive(Schema)]`, `#[derive(Params)]` and `#[derive(Validate)]`. The validation
  errors are the same as before. Handlers take `Path`, `Query` and `State` from the kernel, and answer with `NoContent` or
  `Download`. `autoxide_kernel::async_trait` replaces the `async-trait` crate. The sample module `notes` uses all of it,
  and its OpenAPI contract is unchanged.
- Module `mail`: bounce records and a suppression list for all mail, per tenant. A recipient address
  the receiving server refuses for good (SMTP 5.1.1, 5.1.2, 5.1.3, 5.1.6, 5.1.10; sender-side errors,
  full mailboxes and oversized mail are not counted) is recorded; after
  `AUTOXIDE_MAIL_HARD_BOUNCE_LIMIT` hard bounces at least 24 hours apart it is suppressed for that
  tenant and new mail to it is skipped and counted. `GET /api/v1/mail/bounces` (`?email=`, `?suppressed=`), `/stats`,
  `POST /api/v1/mail/bounces/{id}/release`, `DELETE /api/v1/mail/bounces/{id}`; permissions
  `mail.bounces.read`, `mail.bounces.manage`; records kept `AUTOXIDE_MAIL_BOUNCE_RETENTION_DAYS`.
- Guide [Connecting MCP clients with OAuth sign-in](docs/guides/mcp-oauth.md) (English and Vietnamese): the settings,
  what the interface's consent page calls, connecting Claude, ChatGPT, Claude Code and other clients, revoking, common
  errors. CI signs in with the official MCP TypeScript SDK client against a real server on SQLite and PostgreSQL.
- OAuth 2.1 protected resource discovery for MCP and REST (MCP authorization 2026-07-28): RFC 9728 metadata at
  `/.well-known/oauth-protected-resource/mcp`, `/mcp/{module}` and `/api/v1`, RFC 8414 metadata at
  `/.well-known/oauth-authorization-server`, `resource_metadata` in every `WWW-Authenticate` challenge, audience
  checks for OAuth access tokens (RFC 8707) and `403 insufficient_scope` challenges for step-up (also in
  `_meta["mcp/www_authenticate"]` of an MCP tool error). The documents answer `404 oauth_unavailable` until a module
  provides the authorization server and `AUTOXIDE_HTTP_PUBLIC_URL` (without a path) is set.
- `Principal::credential()` and `Principal::is_session()` tell a sign-in session from an API key or an OAuth grant;
  actions reserved for a person's own session use them.
- OAuth 2.1 authorization server for MCP clients (MCP authorization 2026-07-28): Claude, ChatGPT and other MCP
  clients connect without pasting a key. Clients identify with a Client ID Metadata Document (or the deprecated
  dynamic registration at `POST /api/v1/auth/oauth/register`), the browser goes through
  `GET /api/v1/auth/oauth/authorize` (PKCE `S256` only, `iss` in every answer) to the interface's consent page
  (`AUTOXIDE_AUTH_OAUTH_CONSENT_URL`), which reads and decides the request with `/api/v1/auth/oauth/requests/{token}`.
  Opaque access tokens (`axo1_…`) carry only the permissions the person chose, never more than they currently have;
  refresh tokens rotate, and reusing a code or an old refresh token revokes the approval. People list and revoke
  their approvals at `/api/v1/auth/me/oauth-grants`; administrators with `auth.oauth_grants.manage` at
  `/api/v1/auth/oauth-grants`. Locking an account, signing out everywhere or changing the password with sign-out
  revokes its approvals; automation rules made through a client pause when its approval is revoked.
- Kernel: `ReferenceSource::referrers_page` (one page of the records of a module that point at a record, each with
  its key, `KeyedReferrer`) with a default implementation, so sources written before it keep compiling; the default
  reads at most `REFERRERS_PAGE_FALLBACK_LIMIT` referrers through `referrers` and cuts the page in memory — override
  it with a keyset page in your database. Build a `KeyedReferrer` with `KeyedReferrer::new(key, referrer)`: the
  struct is `#[non_exhaustive]`.
- Setting `AUTOXIDE_COMPLIANCE_PURPOSES_TENANT_MAX`: most processing purposes of its own a tenant may add (default
  200).
- Kernel: `autoxide_kernel::pagination::NaturalOrderPageQuery` (lists in a natural order: `order` defaults to
  `asc`), `SortChoicePageQuery` with `into_request` (lists with a `sort` choice: the default of
  `order` follows the chosen sort) and `page_of` (one page of a list that is not in the database).
- MCP list tools `address.list_provinces`, `address.list_communes`, `content.legal_templates`,
  `conversations.list_calls`, `notifications.list_my_devices`, `notifications.list_kinds` and `reporting.kinds`
  take `count` (`true`: also return `pagination.total` on the first page), like the `count` query parameter of REST.
- Kernel: `autoxide_kernel::mcp::PageInput::with_count` — a list tool built on `PageInput` passes its `count` input
  (`true`: also return `pagination.total` on the first page), like the `count` query parameter of REST.
- SMS templates per tenant: the text of every SMS that carries a one-time code can be set by the tenant to
  match the template it registered with the carriers for its SMS brandname — tenant settings
  `compliance.sms_template.phone_verification`, `compliance.sms_template.sign_in`,
  `orders.sms_template.order_lookup`, `orders.sms_template.address_change` and
  `bookings.sms_template.guest_code` (group `sms_template`, `PUT /api/v1/kernel/settings/{name}`). A template
  must contain `{code}` exactly once and only the placeholders of that message; unset, the previous text is
  sent. Kernel: `autoxide_kernel::sms::{check_sms_template, fill_sms_template, tenant_sms_text,
  SMS_TEMPLATE_GROUP}` for modules that send codes.
- Kernel: `autoxide_kernel::pagination::text_key_cursor` and `PageRequest::text_key_after` — cursor for a list
  ordered by an expression that is not one column (such as a `SUM` of a `GROUP BY`), so it pages with a keyset in
  the database. The `analytics` ranking lists use it.
- Releases carry a CycloneDX SBOM of the Rust crates (`autoxide.cdx.json`), the texts of the third-party licenses (`THIRD-PARTY-LICENSES.html`, also inside the image and every binary archive), and the binary embeds its dependency list (`cargo auditable`). Docs are published per release at a versioned documentation site (GitHub Pages).
- `autoxide rollback --to X.Y.Z` brings the main database and every tenant database back to the migrations of an
  earlier release (0.14.0 or later). `--dry-run` lists, per database, the migrations to revert and the tables and
  columns that would be dropped with how many rows they hold (on SQLite on a copy, on PostgreSQL inside a rolled-back
  transaction bounded by `--lock-timeout-seconds`); a real run needs `--yes`, and `--accept-data-loss` when data is
  dropped. Modules a binary adds itself are left as they are unless `--revert-untracked`. It is recorded as a
  migration run of kind `rollback`.
- `autoxide migrate manifest` prints every migration of the program, without a database.
- `GET /api/v1/kernel/placements/migrations` returns `kind`, `from_version` and `to_version` for each run.
- Module authors: `MigrationTrait::irreversible()` (default `false`) marks a migration a rollback must not cross.
- Rate limit per tenant, on top of the limits per client address and per API key:
  `AUTOXIDE_HTTP_RATE_LIMIT_TENANT_PER_MINUTE` / `_BURST` (off by default), or the plan's limit
  `kernel.api_rate_per_minute`; over it REST and MCP answer 429 `tenant_rate_limited` with
  `Retry-After`. Counted in memory or shared through the database like the API key limit. Only
  signed-in callers count, against the tenant they act in (their own, or one that delegated work to
  them): anonymous requests (whatever tenant they name), inbound webhooks, platform staff and support
  access never use a tenant's budget, and a sync batch counts once.
- AI daily token limit per plan: limit `ai.daily_tokens`; a plan that does not set it keeps
  `AUTOXIDE_AI_DAILY_TOKEN_LIMIT`. `GET /api/v1/ai/status` adds `daily_token_limited`, telling "no
  limit" apart from a limit of 0.
- Tenant settings `catalog.locales`, `menus.locales` and `menus.default_locale` (languages of product
  texts and website menus per tenant, like `content.locales`).
- Sign-in policy per tenant (organization settings at the tenant's root unit): `auth.staff_registration`
  (self-registration of staff, also for a first OIDC sign-in), `auth.password_min_length`,
  `auth.session_days` and `auth.totp_issuer`. A tenant can only make the server's policy stricter: a
  shorter password minimum or a longer session than the server's is ignored.
- Passkeys per tenant: tenant setting `auth.passkey_rp_id`, one of the tenant's verified domains, checked
  when set and at every use. Kernel: `TenantSetting::own_domain` and `SiteLinks::own_domain` for any
  setting whose value must be a domain the tenant has verified. `GET /api/v1/kernel/client-config` gives
  `auth.passkeys`, `auth.passkey_rp_id` and `auth.self_registration` for the request's tenant.
- CORS follows tenants' domains: in multi-tenant mode a page at `https://<domain>` of a tenant's
  verified domain may call the API from a browser without listing it in
  `AUTOXIDE_HTTP_CORS_ORIGINS` and without a restart, but only for that tenant (otherwise
  `403 tenant_origin_mismatch`; from such a page a refresh token, email link or export link of
  another tenant counts as wrong); the MCP endpoint's `Origin` check uses the same rule. A removed domain loses it at once
  on the server that removed it and within `AUTOXIDE_TENANCY_CACHE_SECONDS` on the others.
- Per-tenant links in mail: each mail link (password reset, email verification, invitation, sign-in
  link, email-change report, guest support ticket, complaint tracking, back-in-stock confirmation,
  advertising unsubscribe, comment verification and unsubscribe, newsletter confirmation and
  preferences) is a tenant setting of group `link` (`<module>.link.<page>`) holding the whole page
  address, path included. It is accepted only on a host the tenant controls (one of its verified
  domains, the address of its `kernel.public_url`, or the platform host of `AUTOXIDE_HTTP_PUBLIC_URL`
  on its default port), never on another tenant's verified domain, and checked again on every mail;
  otherwise the server's address is used as before. Support, compliance, inventory and notifications mails now follow `kernel.public_url`
  too.
- Tenant settings `newsletter.postal_address` (defaults to the owner's name and address in the tenant's
  legal profile, then `AUTOXIDE_NEWSLETTER_POSTAL_ADDRESS`), `content.embed_hosts` and
  `analytics.allowed_hosts`.
- Threat model of the core in `docs/THREAT_MODEL.md` (Vietnamese: `docs/THREAT_MODEL.vi.md`): STRIDE per trust
  boundary (HTTP, MCP, kernel, modules, database, placement, external providers, AI), the existing control for each
  threat with a pointer to the code or decision, open items, and suggested focus areas for outside penetration testers.
- `autoxide config` and the start-up log of `autoxide serve` name an `AUTOXIDE_…` variable that is not a setting (a
  misspelling such as `AUTOXIDE_PORT` used to be ignored in silence) and suggest the closest real name.
- `docs/DEPLOY.md`: "B+", one binary with PostgreSQL from scratch, and "3b", trying the binary by hand (`migrate up`
  before `serve`, `AUTOXIDE_HTTP_ADDRESS`, a first request with data); the README points to them for people without Docker.
- Module `ledger`: `POST /api/v1/ledger/payments/{id}/simulate` (MCP tool `ledger.simulate_payment`)
  completes a simulated payment inside a sandbox, through the same path as a partner notification
  (`succeeded`, `failed`, or `needs_review` for another amount). Off unless the operator sets
  `AUTOXIDE_LEDGER_SANDBOX_SIMULATION=true`; only for `pending` payments created inside the sandbox.
- Testkit: `McpClient::with_header` sends an extra header (e.g. `Autoxide-Tenant`) with every MCP request.
- Docs: "Try it without real accounts" in the shop guide (several tenants, `autoxide tenant create`, a sandbox,
  `Autoxide-Tenant` on every call, completing the simulated payment); the shop guide also covers the tax profile,
  an invoice series without an e-invoice provider, your own delivery fees, payment method values and how a guest
  gets an `Order-Token`; the promotions guide has a complete coupon sequence (notice province setting, code,
  notice record, activation) and explains `promotions.reason.no_reference_price`. The sandbox guide no longer

### Changed

- Compatibility policy (`docs/COMPATIBILITY.md`): before 1.0 a minor release may break the HTTP API too,
  like every other contract; each break is listed under **Changed** or **Removed** with what to do
  instead. From 1.0.0 the policy applies in full and nothing in `/api/v1` breaks. The earlier wording
  said both that a `0.x` minor may break any contract and that the HTTP API already could not.
- Pending approval requests (`x-approval`) can only be decided from a person's sign-in session: an API key of
  kind `human` or an OAuth client no longer approves or rejects them, and sees only its own requests.
- Automation runs now follow their rule: editing a rule (even only renaming it) or enabling it again stops its runs
  still in progress or waiting, with `automations.rule_changed`, and deleting a rule ends its waiting runs with
  `automations.rule_not_active`. Before, a run kept the rule as it was when it started and finished it. Start the rule
  again if a stopped run was still needed.
- `autoxide backup` no longer needs the database migrated first: a backup keeps the schema of its source exactly as
  it is (`backup.json` lists the migrations it holds), so you can back up right before an upgrade and the release you
  upgrade from can restore it. Scheduled backups do the same. It refuses a database with no Autoxide tables (often a
  wrong `DATABASE_URL`) instead of writing an empty backup.
- `autoxide restore` checks the whole backup before it touches the target, and refuses with a clear message a backup
  made by a newer release or holding data of modules that are turned off or missing; the target stays empty, so you
  can fix the setting and run it again.
- `autoxide backup --all` also backs up every placement, with its own file storage, into `placements/<name>/`;
  `backup.json` of the main database is written last, so an interrupted run never looks complete.
  `autoxide restore <dir> --placement <name>` restores one into that same placement, once its database is empty
  again; the placement is marked `migrating` meanwhile.
- **Breaking:** public content search (`GET /api/v1/content/public/posts?q=`, the word part of
  `GET /api/v1/content/public/search`, content suggestions) matches whole words, ignoring case and accents
  (`ca phe` finds "Cà phê"), and word prefixes from 3 letters (`lat` finds "Đà Lạt"). It no longer matches any
  substring (`alat` finds nothing). It returns the 1,000 newest matching entries, after the other filters (website,
  category, author); a search that takes longer than 2 seconds answers `503` rather than a partial list. Text
  written without spaces (Chinese, Japanese, Thai…) is one long "word": a run longer than 64 characters is not
  indexed, and a run is found by its beginning.
- `GET /api/v1/content/public/posts?q=` now shares the public search limits
  (`AUTOXIDE_CONTENT_PUBLIC_SEARCH_CONCURRENCY`, `AUTOXIDE_CONTENT_PUBLIC_SEARCH_PER_ADDRESS_PER_MINUTE`) and
  answers `429` past them. `AUTOXIDE_CONTENT_PUBLIC_SEARCH_CONCURRENCY` now counts searches and content suggestions
  together on each database and is lowered automatically to the read pool minus 2, so public search never takes
  every read connection; a quarter is kept for suggestions, which leave out posts and pages when it is full.
- The Docker image is now distroless (Debian 13 `cc` base): no shell, `cat`, `rm`, `curl` or package manager, smaller to patch. It still runs as user `10001`, so existing volumes keep working. **Action needed:** anything that used `docker exec … sh`, `cat` or `curl` inside the container must use `docker debug` / `kubectl debug` or an `autoxide` command instead. The quickstart commands `exec autoxide cat data/initial-admin-password` and `exec autoxide rm data/initial-admin-password` are replaced by `exec autoxide autoxide initial-password` and `exec autoxide autoxide initial-password --remove`.
- New command `autoxide initial-password [--remove]`: prints (or deletes) the file where `autoxide serve` wrote the generated password of the first administrator (`AUTOXIDE_BOOTSTRAP_ADMIN_PASSWORD_OUT`). Exit 1 when the file does not exist, 2 for invalid configuration. It also works outside Docker.
- New command `autoxide healthcheck` (exit 0 when `/health/ready`, or `/health/live` with `--live`, answers 200): the image's `HEALTHCHECK` and the `app` service of `compose.yml` use it, so `docker compose ps` shows `healthy`. It reads only `AUTOXIDE_HTTP_ADDRESS`, so it needs no other setting; a server that never started (for example for a missing setting) simply does not answer and the container reports `unhealthy`.
- Cancelling an invoice whose e-invoice provider cannot cancel a sent invoice (SePay eInvoice, e.g. when the seller has
  no tax profile) now returns `409 invoices.einvoice_cancel_unsupported` (parameter `provider`) instead of
  `422 einvoice.not_supported`; issue an adjustment or a replacement instead (D-20261127-einvoice-cancel-unsupported).
- Contributors: `./gate.sh` (including `GATE_LOCAL=off ./gate.sh --quick`) type-checks the TypeScript SDK and the guide
  examples with `tsc --noEmit` when Node.js is installed and the SDK, the contract or `docs/guides` changed; it clears
  the old extracted examples first, reinstalls `node_modules` when `package-lock.json` changed, and runs when the
  branch point cannot be found (shallow clone) (D-20261127-gate-tsc).
- An idle server runs far fewer SQL statements in the background: each second the event dispatcher and the job
  worker ask in one statement per database which modules have work, instead of querying every module's table.
  Delivery of events and jobs is as fast as before.
- For authors of external modules: `KeyedReferrer` (returned by `ReferenceSource::referrers_page`) is now
  `#[non_exhaustive]`. Build it with `KeyedReferrer::new(key, referrer)` instead of a struct literal, so fields can be
  added later without breaking your module.
- The compliance, AI, tax and money guides now say what core does not do yet after the first legal review, and
  what the deployer covers meanwhile: listing goods is not blocked by seller identity verification yet; no
  handling of children's personal data; AI, mail, SMS and storage providers abroad are not added to the
  processing register by themselves; marketplace withholding is computed and booked but not withheld on each
  payout, certified or declared. The module guide cites Decree 356/2025/ND-CP instead of Decree 13/2023/ND-CP.
- Legal rules updated after the first legal review (all need checking against the original texts): the Ministry
  of Industry and Trade checklists `moit.checklist.*` and the case deadlines `cases.deadlines` have version 2 from
  1 July 2026 citing the E-commerce Law 122/2025/QH15 and Decree 248/2026/ND-CP (replacing Decrees 52/2013 and
  85/2021), with the transition notes; `privacy.subject_requests` version 2 cites Decree 356/2025/ND-CP (72 hours
  kept, stricter) and lists the days to carry a request out; the promotions pack `vn` version 2 cites Decree
  239/2026/ND-CP from 26 June 2026 and keeps the 50% discount cap and 120 discount days a year as cautious
  defaults; data residency docs cite the Cybersecurity Law 116/2025/QH15.
- On a marketplace (`kernel.business_model = marketplace`) with module `compliance`, a product of a seller (any branch
  other than the tenant's root) can only go `active` once the seller's identity is verified; otherwise
  `POST /api/v1/catalog/products/{id}/status` and the MCP tool `catalog.set_product_status` answer
  `compliance.kyc_required` (403). The seller is the owning branch or a branch above it (below the root); one
  verified branch in that chain is enough. With module `compliance` turned off, goods of a seller on a marketplace
  cannot go on sale (`catalog.seller_verification_unavailable`, 403). Whether verification is required follows the dated rule `kyc.required_activities`
  (E-commerce Law 122/2025/QH15, Decree 248/2026/ND-CP Article 18). Goods already on sale are not re-checked.
- The start-up log line "migrations applied" no longer lists every migration name (hundreds on a first start); it
  shows the count, and the names are at `debug` level.
- Issuing an invoice document when the unit has no active series for the document's kind and year of issue now
  returns `409 invoices.no_active_series` (parameter `year`) instead of `404 invoices.series_not_found`; create a series
  with `POST /api/v1/invoices/series`. `invoices.series_not_found` now only means the series pinned on the document
  does not exist (D-20261127-no-active-series-code).
- New 403 answers where `auth.roles.manage` alone used to be enough: `PUT /api/v1/auth/users/{id}/roles` and
  `PUT /api/v1/auth/users/{id}/memberships` when a role given or taken away is beyond the caller, `DELETE
  /api/v1/auth/roles/{id}` when the role is beyond the caller (`auth.role_beyond_you`), and `PUT
  /api/v1/auth/roles/{id}` when the change adds, widens or unbans a permission the caller lacks
  (`auth.permission_beyond_you`) or turns off `requires_mfa` of a role the caller could not give
  (`auth.role_beyond_you`). Allowed before 1.0 by the compatibility policy (D-20261125-api-break-before-1-0).
- `autoxide migrate up` and `down` print one line per module when there are many migrations (a first start has about
  four hundred); `autoxide migrate status` lists each one. `migrate down --steps 0` is refused.
- `backup` and `restore` no longer log a line per table (they print the summary); the per-table lines are at `debug`.
- While the server drains (graceful shutdown), the `/health/ready` answers `shutting_down` are logged at `debug`, not
  `ERROR`; request log lines carry `tenant_id` once.
- A database that cannot be reached (wrong port, server down) is reported with its root cause next to the pool
  timeout; an error in `.env` names the variable (and never echoes the line, which may hold a password).
- The "SMTP is not set" warning is logged when mail is first written to a file, not at the start of every command.
- The error text of `copy`, `backup` and `restore` names the right command (`autoxide backup`, `autoxide restore`).
- `AUTOXIDE_AUTH_TOKEN_SECRET` is described as recommended, not required, in `docs/DEPLOY.md`.

  person's data export includes their part and deleting an account deletes the person's data in them;

### Security

- Automation rules pause (reason `owner_access_revoked`) when the account they run as is locked out, recovered by
  email, has every session revoked with a password change, or is disabled or deleted; a person with the right
  permissions must check and enable them again. Whenever a rule stops being `active` (any pause, disabled), its runs
  still waiting end with `automations.rule_not_active`; a run that started before the rule was edited or enabled again
  stops with `automations.rule_changed` instead of finishing old actions under the new person responsible. This also
  happens when the owner changes their password and signs out everywhere. Rules created, edited or enabled through a
  signed-in session can no longer use a permission their author did not have at that time, even if the account gains
  it later (the limit is by permission name; rules created with an API key already worked this way).
  **Action needed:** rules saved before this release have no such limit until someone edits or enables them again;
  review and re-enable the rules that matter.
- New kernel event contract `autoxide_kernel::accounts::ACCESS_REVOKED` (`auth.access_revoked`), emitted by `auth`
  whenever every way into an account is cut.
- Passwords follow NIST SP 800-63B-4: a new password must be 15 to 128 characters (was 12) and must
  not be on a list of about 56,000 common or breached passwords (15 characters or more) that ships
  inside the binary (checked offline and case-insensitively). Every way of setting a password checks it: sign-up,
  administrator and `autoxide user create`, first password, change, reset and accepting an
  invitation. A refused password gets `422` `validation_failed` with field code `common_password`.
  **Upgrade note:** existing passwords keep working, the rules apply only when a password is set;
  clients that check the length themselves should use 15, and a tenant's
  `auth.password_min_length` of 12 to 14 now counts as 15 (it is still shown as stored). A
  bootstrap administrator password (`AUTOXIDE_BOOTSTRAP_ADMIN_PASSWORD` or `…_FILE`) and scripts
  that call `autoxide user create` must follow the new rules too: with a password of 12 to 14
  characters, or one on the list, `autoxide serve` stops at startup because it cannot create the
  first administrator, and `autoxide user create` refuses the account.
- `Strict-Transport-Security` is on by default in production: when `AUTOXIDE_HTTP_PUBLIC_URL`
  starts with `https://` and `AUTOXIDE_HTTP_HSTS_SECONDS` is unset, responses carry
  `max-age=31536000`. Development (`http://` or no public URL) sends none. **Upgrade note:** set
  `AUTOXIDE_HTTP_HSTS_SECONDS=0` to keep it off, for example while some clients still reach this
  host over plain HTTP.
- Module `content`: public text search (`GET /api/v1/content/public/posts?q=`, the word part of
  `GET /api/v1/content/public/search`, and content suggestions in the shared search box) uses a word index (the new
  table `content_published_words`, the same on both databases) instead of scanning every published entry.
  Each search is limited to the posts shown on the caller's website. The database stops a search statement
  after 2 seconds, or as soon as the request is cancelled (`503 content.public_search_timeout`).
- Content search also loads each meaning index once when several searches ask for it at the same time.
- A public search whose meaning part was cut short no longer uses up the tenant's per-minute budget.
- The CPU work of a cancelled search stops with it.
- Module `auth`: disabling an account (over REST or with SCIM `active: false`), and every path that locks an account
  out, now also revokes the SCIM tokens the account created and stops sign-in providers it configured from linking
  external identities to existing accounts automatically (existing links keep working). A sign-in provider no longer
  links automatically once the person who configured it lost `auth.oidc.manage`. Before, these kept the power of the
  account's later permissions, and enabling the account again brought SCIM tokens back.
- **Action needed:** create the SCIM token from a separate staff account whose email the identity provider does not
  manage. Changing that person's email or disabling them revokes the token the provider is using, and syncing stops
  with `401` (for example when the company moves to a new email domain). After disabling the person who configured a
  sign-in provider, save the provider again from another administrator's account to restore automatic linking.
- Module `auth`: a sign-in provider that gives new accounts a role (`default_role_id`) is checked on every save
  (whoever saves it must be able to give that role) and again at each sign-up: the person who last saved it must
  still be active, hold `auth.oidc.manage` and be able to give that role, or sign-up is refused with
  `auth.oidc_default_role_unavailable`. Recovering an account by email, changing the password with "revoke other
  credentials", and deleting an account also revoke the SCIM tokens and sign-in provider role of that account.
- **Action needed:** sign-in providers with a default role that were saved before this version, or whose configurer
  was disabled, refuse new sign-ups until an administrator saves the provider again.
- Module `auth`: managing API keys follows the credential the request carries, over REST and the MCP tools alike.
  A password session manages every key of its user. An API key lists and revokes only itself: another id answers
  `404`. An OAuth token lists no key and revokes none. Rotating a key needs a password session, checked before the
  key is looked up.
- Revoking a key with `auth.api_keys.manage` (`DELETE /api/v1/auth/all-api-keys/{id}`) needs every permission of the
  key's owner, unless the owner does it from a password session (`403 auth.target_has_more_permissions`).
- `GET /api/v1/auth/me/passkeys` needs a password session (`403 auth.session_required`).
- Managing roles now follows one rule everywhere: you can only give or take away what you have yourself. A role
  you give or take away (`PUT /api/v1/auth/users/{id}/roles`, `PUT /api/v1/auth/users/{id}/memberships`, the MCP tools
  `set_user_roles` and `set_memberships`) must only have permissions you hold as widely, for anyone including

  - Codes per hour are counted per number and client, so strangers using up their share no longer stop the owner from

  - New caps against SMS floods: `AUTOXIDE_COMPLIANCE_OTP_PER_PHONE_ALL_CLIENTS_PER_HOUR` (default 5, all clients) and

- Per-address limits now count one client as one IPv4 address or one IPv6 /64 block, instead of
  the exact IPv6 address: one-time SMS codes (`compliance` sign-in and phone verification, `bookings`
  guest codes), guest order lookup in `orders` and the email + address login lock in `auth`. Before,
  a client owning an IPv6 /64 could rotate addresses and make the shop pay for many SMS. A new
  kernel helper `autoxide_kernel::throttle::address_key` builds such keys, and `cargo xtask check`
  rejects keys built from a raw address.
- Phone sign-in codes: wrong codes now count per phone number and per client (IPv4 address or
  IPv6 /64) of whoever asked for the codes, with a cap five times higher across all clients. A stranger can no longer lock
  someone else's number for a day with two SMS; guessing a code is still capped per number.
  `AUTOXIDE_COMPLIANCE_OTP_WRONG_PER_PHONE_PER_DAY` keeps its name and default.
- Counter sales (`POST /api/v1/orders/pos/sales`): payments that add up beyond the storable range
  return 422 `money.overflow` instead of a server error, and a payment in a currency other than the
  shift's returns 422 `orders.payment_currency_mismatch` instead of being recorded as the shift's
  currency.
- Web push subscriptions (`POST /api/v1/me/push-subscriptions`) refuse endpoints on internal hosts
  (loopback, private networks, link-local such as cloud metadata, `localhost`). The `WebPushSender`
  contract now states that senders must connect only to public addresses.
- Records can no longer be attached to an organization unit that does not exist in the tenant
  (a made-up id, or another tenant's unit) by a caller with a tenant-wide permission: the shared
  permission decision now checks the unit against the tenant's tree and answers 403
  `org_out_of_scope`, as for a unit outside the caller's scope. This covers every endpoint and MCP
  tool that checks a permission at a unit (menus, products, POS shifts, per-unit settings, ledger,
  shipping, content, invoices…). Catalog import/export, product drafts from images, content campaign
  drafts, the public cart and the public restock alert answer 404 `org_not_found` for an unknown
  unit. A sandbox created with an unknown `role_id` no longer falls back to the `admin` role.
  New kernel helpers: `OrgTree::contains` and `OrgTree::ensure_exists`.

  tenants, every REST operation and MCP tool): report, machine-readable case matrix and the scripts to run it
  again in `docs/security/pentest-2026-11/`. No high or critical finding; the findings and
  where each one was fixed are listed in the report.
- A caller without any of an endpoint's permissions now gets 403 `permission_denied` before anything else is
  checked: before the request body is validated, before `If-Match` is required, and before the record is looked
  up. Callers without access no longer learn which fields are wrong, which endpoints need an `ETag`, or which
  records exist.
- `x-permissions` in the API document now lists every permission an endpoint accepts (18 operations of
  `inventory`, `kernel` tenant exports, `notifications`, `content`, `customers` and `support` were missing one).
- Module `content`: public categories and tags (`GET /api/v1/content/public/terms` and
  `GET /api/v1/content/public/terms/{taxonomy}/{slug}`) only show a term that at least one entry shown on the
  website carries — not one used only by drafts, by entries hidden while a report is handled, or by another
  website of the tenant (PT-11). A menu item pointing to an empty category leads to a 404 until a post carries it.
- Module `analytics`: a new daily limit per network block, `AUTOXIDE_ANALYTICS_EVENTS_PER_DAY` (default 20000), on
  top of the per-minute one, bounds how much one network can skew the reports (PT-12).
- Module `newsletter`: the daily cap on confirmation mails counts per mailbox: letter case, a `+tag` after the name
  and dots in a Gmail name no longer give extra mails (PT-18).
- Module `auth` (SCIM): changing a linked account through a SCIM token also requires the token's creator to be able to
  grant each role the account holds at its unit, not only to have the same permission names (PT-19).
- Public content search (`GET /api/v1/content/public/search`) can no longer slow down the whole server: each
  server process runs at most `AUTOXIDE_CONTENT_PUBLIC_SEARCH_CONCURRENCY` (default 8) public searches at once
  (`429 content.public_search_busy` past it; a search keeps its place until its work has really finished), one
  client address may search `AUTOXIDE_CONTENT_PUBLIC_SEARCH_PER_ADDRESS_PER_MINUTE` times a minute (default 20,
  `429 content.public_search_rate_limited`; a refusal because the server is busy does not count), and a search
  that has not answered after 3 seconds gets `503 content.public_search_timeout`. When the embeddings provider is
  slow, search by meaning is skipped after 1.5 seconds and the results match words only.
- Module `auth`: a SCIM token, and the SCIM group mappings, can no longer give, keep or take away more than the person
  responsible holds (2026-11 security review, P-7). Before, someone holding only `auth.scim.manage` could use a SCIM
  token they created to give accounts a role that a group mapping made by an administrator grants (including
  `admin`), delete accounts with more permissions than their own, and remove an administrator's group mappings.
  Now adding or removing members of a mapped group, deleting a group, deleting or changing a SCIM user with more
  permissions, and deleting a group mapping all check the token creator's (or the caller's) current permissions and
  answer `403` (SCIM error body; REST: `auth.role_beyond_you`) without changing anything.
- **Action needed:** a SCIM token's power follows its creator at the time of use. Create the token from an account
  that holds every role your group mappings give, and **rotate it when its creator leaves or loses roles** —
  otherwise removing people from groups and disabling leavers fails in the identity provider with `403`.
  `GET /api/v1/auth/scim/tokens` now shows `creator_status` (`active`, `disabled`, `deleted`, `missing_permission`)
  for each token.
- `POST /api/v1/auth/scim/group-mappings` now lists the members who received the role (`granted_user_ids`). A group
  without rules can be filled by anyone holding a SCIM token: check its members before mapping it to a powerful role.

  Content Security Policy, not every file on the CDN; styles and fonts no longer come from the CDN

  `0`: no limit); over it new connections wait instead of exhausting file descriptors. A connection
  that sends nothing at all is closed after 30 seconds, like a slow request header (L-10).

  `AUTOXIDE_PROVIDER_MAX_RESPONSE_BYTES` (default 16 MiB); a larger answer fails the call as if the
  provider were unreachable (I-2).

  (`.github/gitleaks/Dockerfile`) that Dependabot updates (I-5).
- Module `auth`: `POST /api/v1/auth/me/password` takes `revoke_other_credentials`; `true` also removes every
  API key, passkey and external sign-in link of the account, and any pending password-reset link, as a
  password recovery does (L-7 of the 2026-11 security review). Without it they keep working, as before.
- Module `ledger`: a payment's `return_url` must be on one of the tenant's own addresses: an `https://` address
  on a verified domain, or an origin listed in the new tenant setting `ledger.payments.return_origins`. Any
  other address is refused (field error `ledger.return_url_not_allowed`; through checkout and `payment-link`
  of `orders`: `orders.return_url_not_allowed`), so a payment link cannot send the buyer to an outside site
  after paying (P-5). The partner receives the address as checked, in its normalized form. **Action needed:** a shop that sends `return_url` lists its
  website's origin in `ledger.payments.return_origins` (or verifies its domain) before upgrading.
- Tenant domains: a domain another tenant has only claimed (`pending`) no longer blocks you for 7 days. Several
  tenants may wait on the same domain; the first to verify it gets it, and the others' claims turn `failed`
  with the reason (P-4 of the 2026-11 security review).
- Module `automations`: a rule of an organization unit other than the tenant's root starts only for events of
  that unit or its branch (the event's `org_id`); events naming no unit reach only tenant-wide rules (L-8).
- Module `orders`: a `return_url` that is not an http(s) URL is reported as `orders.return_url_invalid`, apart
  from `orders.return_url_not_allowed` (an address that is not the shop's).
- HTTP server: an open WebSocket counts towards `AUTOXIDE_HTTP_MAX_CONNECTIONS` for as long as it stays open, and
  a connection that has sent nothing yet no longer delays a graceful shutdown (L-10 follow-up).
- The permission gate now requires a signed-in caller for every operation marked `x-permissions: []` (any signed-in
  caller), before the handler runs, even when the handler itself does not read the caller. Before, such an operation was
  protected only if its handler took the caller as input.
- The `kernel.api_requests` plan quota counts only signed-in callers in their own tenant: an anonymous
  request naming a tenant (`Autoxide-Tenant`, `Host`) no longer uses up that tenant's quota.
- `kernel.public_url` and mail link settings no longer accept another tenant's verified domain
  (`422 kernel.public_url_not_allowed` / `kernel.link_host_not_allowed`), nor a domain the tenant
  lost (revoked, or failed its DNS recheck) until it is verified again. When a domain is revoked, fails
  or moves to another tenant, mail links stop going there — on other servers within
  `AUTOXIDE_TENANCY_CACHE_SECONDS` (default 10 seconds).

### Fixed

- Module `compliance`: a late result of an old identity check no longer verifies a profile again
  after it was revoked, approved by hand, or moved on to a newer check; that attempt is kept as
  `superseded`.
- Module `compliance`: two profiles with the same identity document verified at the same time no
  longer both become `verified`; the later one waits for a reviewer (`duplicate_document`). New
  migration `m0020_kyc_verified_document`.

  target is shown again (`compliance.target_restored`) instead of staying hidden.

  migrate in parallel; the others get `kernel.migration_run_busy` (409). New kernel migration
  `m0039_migration_run_active_key`.
- Module `bookings`: several people who are the first to book the same class at the same time all
  get a seat while the class has room, instead of `bookings.slot_taken`.
- Module `conversations`: an automatic reply is no longer added to a conversation that was just
  closed or handed to a person; marking as read from two devices at once never moves the read
  cursor back.
- Module `automations`: runs started at the same time can no longer go over
  `AUTOXIDE_AUTOMATIONS_MAX_RUNS_PER_HOUR`.
- Module `content`: banners created at the same time can no longer go over the placement's
  `max_items` or share a position.
- Module `newsletter`: confirming and unsubscribing at the same time always ends unsubscribed.
- Module `tax`: two changes of a tax profile with the same `If-Match` no longer both pass; the
  later one gets `412`.
- Module `orders`: two checkouts of the same cart with different `Idempotency-Key`s no longer
  create two orders; the later one gets `orders.cart_closed` (409) and its holds are released.
- Module `orders`: closing a POS shift waits for sales being written and counts them in the expected
  cash; a sale can no longer be recorded in a shift that was just closed (`orders.shift_not_open`).
- Module `plans`: voiding a billing period while its invoice is being issued now also cancels that
  invoice; a voided period never keeps a live VAT invoice.

- Module `promotions`: approving and rejecting a seller's application at the same time no longer

  is being reviewed.
- Module `promotions`: two promotions activated at the same time can no longer both pass the legal

- MCP endpoint: protocol errors answered with HTTP 400 or 404 now carry the JSON-RPC error body the

  protocol versions recognize the server as a `2026-07-28` server.
- Tenant data export (`/api/v1/kernel/tenants/{id}/exports`) writes date columns as `YYYY-MM-DD`; they were
  exported as `null`, so the dates were missing from the file.
- Module `auth`: removing two sign-in links of an account at the same time can no longer remove
  both and lock the owner out; the "last way to sign in" check now runs inside the transaction,

  acceptance fails) or is accepted (the revoke answers `409`) — never both; revoke no longer
  emits an event for an invitation that was accepted in the meantime.
- Module `automations`: enabling a rule checks that it is still the version the enabler validated
  (`412` otherwise) — an agent edit in between can no longer be enabled under a human's
  permissions without review. Concurrent edits get distinct version numbers.
- Module `bookings`: changes to one booking are serialised — two reschedules at once no longer
  leak a slot or release the old session seat twice, and a deposit that arrives while the hold
  expires no longer confirms a booking whose slot was already released (Postgres).
- Module `catalog`: writes to a product (status, variants, documents) lock the product row, so a
  product cannot go on sale while a required document is being removed, and two concurrent variant
  edits no longer both emit `catalog.preorder_date_changed` (Postgres).
- Module `comments`: hiding a comment target while the owning module changes its close date no
  longer loses the hide (Postgres); `If-Match` on a target is checked on the locked row.
- Module `compliance`: two KYC callbacks for the same attempt processed at once record the result
  and emit `compliance.kyc_verified` once. Adding tracking tags at the same time bumps the cookie
  policy version for every new provider (visitors are asked again), and creating the banner twice
  at once no longer fails with `500` (Postgres).
- Module `invoices`: a replacement or adjustment issues only while the original is still
  correctable; a second draft replacing the same invoice (issued at the same time or later) is
  refused with `invoices.not_correctable` instead of booking the revenue twice.
- Module `ledger`: postings lock their accounts before checking status and floor, so raising a
  floor or closing an account at the same time can no longer let a posting through below the new
  floor or into the closed account (Postgres). Account updates no longer overwrite a concurrent
  change.
- Module `notifications`: registering the same push endpoint or device token twice at the same
  time keeps a working subscription — the stored secret is always sealed for the row's own ID.
- Module `promotions`: pausing and ending (or two activations of) the same promotion at the same
  time no longer both succeed from the old status — the loser gets `409` instead of a `200` that

  happen (Postgres). Edits and deletes read the status under the same lock.
- Module `shipping`: two COD statements that list the same shipment (different references, or
  one statement repeating a line) settle it once — the carrier COD was credited twice on Postgres
  (and for a repeated line on SQLite too). Two people resolving the same COD discrepancy at once:
  the second gets `409` instead of overwriting the first resolution.
- Module `support`: a message sent while the ticket is being closed no longer reopens the closed
  ticket on Postgres; concurrent status changes no longer both start from the old status; an
  automatic reply re-checks inside its transaction that the ticket is still open and that no other
  automatic reply got in first.

### Security

- Module `bookings`: parallel guesses of a guest phone code all count towards the five-attempt

- Module `orders`: guesses of a guest order-lookup code are counted before the code is checked,

### Changed

- SQLite: the write connection runs `PRAGMA optimize` when it opens and closes, so the query planner has
  statistics for large tables (step 39). Without them a comment thread on a database with a million comments
  scanned most of the table (3.7 s a request); now 0.4 ms for the query. PostgreSQL is unchanged (autovacuum).
- Counting failed attempts (sign-in lockout and other throttles) takes one SQL statement instead of up to four:
  60–75% more attempts per second, except many attempts on one email at once on PostgreSQL, which still queue on
  that email's counter.
- Faster signed-in requests: the user and their permissions are read in one SQL query instead of two on every
  request (access token and API key); `GET /api/v1/auth/me` and the MCP tool `auth.whoami` need three queries in
  all instead of seven, and `GET /api/v1/auth/users` one query per page for the account facts instead of two.
  Responses are unchanged.
- `notes` (the example module) keeps its notes per organization unit: each note has `org_id` (existing notes belong to
  the root unit), `notes.read` and `notes.write` follow the scope of the role (`own`: only your own notes — what they
  meant before; `unit`, `subtree`; `tenant`: every note), and creating a note takes `org_id` (`notes.org_required`
  when you work in several units and give none). A role that grants `notes.read` for the whole tenant now sees every
  note of the tenant: give it with scope `own` to keep personal notes.
- The `detail` of some errors no longer names an endpoint: it says what the user can do (`auth.wrong_password`,
  `auth.password_already_set`, the token errors of `auth`, `media.item_in_trash`…). Which endpoint to call is in the
  description of the response in `docs/openapi.json`. Codes are unchanged.
- For module authors: `Authenticator::authenticate` takes a second argument, the `TenantHint` of the request
  (domain and `Autoxide-Tenant` header). `Principal` carries a tenant (`tenant_id`, `in_tenant`, `operator_from`).
  Handlers may take `tenant: TenantContext` (`autoxide_kernel::tenancy`), and the module start context gives the
  `DatabaseRegistry` (`StartContext::tenancy`).
- For module authors: the kernel's helper tables (`<module>_events`, `_jobs`, `_throttle`, `_tokens`,
  `_antispam_nonces`) carry `tenant_id`; a module adds one migration,
  `tenancy::migration::adopt("…", vec![event::tenant_table("<module>"), job::tenant_table("<module>"), …])`, that
  moves the existing rows to the default tenant. Every call that writes or reads them names the tenant:
  `Outbox::record(conn, &tenant, …)`, `JobQueue::enqueue(conn, &tenant, …)` (and `enqueue_database` for a job of
  the whole database), `OneTimeTokens::{issue, consume, recent, revoke, forget}(conn, &tenant, …)`,
  `Throttle::new(module, limit, window)` without a database and `Throttle::{check, hit, record, refund,
  clear}(&tenant, key)`, `Throttle::purge(&database, before)`, `SpamGuard::check(&tenant, …)` and
  `Checked::claim(conn, &tenant, …)`. `Delivered` and `JobContext` carry the tenant (`Delivered::new(tenant, …)`,
  `JobContext::for_tenant` / `for_database`; `JobContext::tenant` is `None` for a job of the whole database).
  `Claim::claim` takes a `ClaimRequest`. `Modules::worker(concurrency)` and `Modules::dispatcher()` no longer take
  a database: they run on every database of the registry, and the worker shares the free slots fairly between
  the tenants that have jobs due. For tests: `TestDatabase::extra_database`.
- For module authors: every kernel trait that reaches the data of a customer names the tenant:
  `PersonalData::export(&tenant, user_id)`, `ResourceResolver::{resolve, resolve_many, children}(&tenant, …)`,
  `BadgeResolver::badges(&tenant, …)`, `Mailer::send(&tenant, mail)`, `TextModel::generate(&tenant, prompt)`,
  `Embedder::embed(&tenant, …)`, `IdempotencyStore::{begin, complete, abandon}(&tenant, …)`,
  `PostingVerifier::is_verified(&tenant, user_id)`, and the matching `ResourceDirectory`,
  `PersonalDataExport` and `PostingVerification` methods. An MCP tool's handler receives the tenant of the
  request first: `Tool::new(name, description, |tenant: TenantContext, principal: Principal, input| …)`. The
  `api` traits of modules take it too: `autoxide_auth::api::{Users, Accounts, AccountRecovery}`,
  `autoxide_media::api::Media`, `autoxide_notes::api::Notes`, `autoxide_content::api::LegacyMenus`.
- For module authors: the trait `autoxide_auth::api::AccountRecovery` has a new method `remove_passkeys`; only
  `auth` implements it.
- Form tokens (`GET /api/v1/antispam/token`) and `Idempotency-Key` scopes belong to one tenant: a token or a key
  of one tenant means nothing in another. `SpamGuard::issue` takes the tenant. Nothing changes for the default
  tenant: tokens and keys already handed out keep working.
- Interface flags (`/api/v1/me/flags`) are kept per tenant: the same account in two tenants has two sets.
- Internal, no change in behaviour: the code of `newsletter`, `comments`, `media` and `forms` is grouped by
  feature like `content` and `auth`, and the kernel's files sit in private groups (`contracts`, `data`,
  `security`, `ops`, `values`). Every public path (`autoxide_kernel::ai::TextModel`, …) is unchanged, and a
  test keeps it so.
- For contributors: the tests run about twice as fast. Dependencies are built with `opt-level = 1` (and the password
  hash `argon2` with `opt-level = 3`) in dev and test builds — your own code stays unoptimised, so rebuilds take
  as long as before. `./gate.sh --quick` tests only what changed since its last green run (not since `main`), and
  both gates run the test binaries in parallel (`cargo xtask test-all` in the full gate).
- Contributing: pull requests no longer edit `CHANGELOG.md`; they add a fragment to `changelog.d/`
  (`<name>.<section>.md`), folded into the changelog at release time by `cargo xtask changelog`.
- Module `orders`: events `orders.review_published` and `orders.review_moderated` now carry
  `product_rating` (`count`, `sum`: the product's current totals), which `catalog` uses for ratings.
- Search by meaning is faster on large sites (step 39): the vector comparison uses the CPU's vector instructions and
  the scan is split over the CPU cores outside the request thread — 50,000 posts in one language (100,000 chunks of
  1,024 dimensions) went from 137 ms to 20 ms on 4 cores, with the same results.

### Fixed

- Event stream (`GET /api/v1/kernel/events`, `/events/ws`): reconnecting with `Last-Event-ID` no longer
  sends that same event again when its live broadcast arrives after the reconnect.
- `catalog`: two storefront rebuilds of the same product running at once on PostgreSQL no longer both
  record `catalog.display_price_changed` (product rows are locked during the rebuild).
- `lettre` 0.11.24 (mail over SMTP): fixes RUSTSEC-2026-0560 … 0565 (STARTTLS reply injection, SMTP command
  injection, panics on malformed replies, wrong recipient for quoted local parts).
- The fake e-invoice provider of `autoxide-testkit` gives the same answer to every status check of one submission, so
  tests no longer fail when two checks run at once.
- `Throttle::hit` no longer lets extra attempts through under concurrent load: an attempt that passed the "is it
  locked?" read just before another attempt locked the key (and reset its counter) now sees the lock returned by
  its own counting statement and is refused. Seen on PostgreSQL under parallel load; SQLite and PostgreSQL alike.
- `cargo build --release` failed in `autoxide-plans` ("queries overflow the depth limit"); debug builds were fine.
- `POST /api/v1/auth/me/reauth` with a wrong authenticator code reported the error on field `code` instead of
  `totp_code`, the field that was sent.

- `GET /api/v1/auth/me` in a tenant entered through a delegation or a support grant answered `401`: it now returns
  the account and the permissions you have in that tenant, with `tenant_id`, `access` (`direct`, `delegation`,
  `support`) and `home_tenant_id`; `GET /api/v1/auth/me/memberships` returns an empty list there instead of `404`.

  bad_request` with the library's raw English text; it now answers `422 validation_failed` with the field in

- `PATCH /api/v1/kernel/tenants/{id}` takes the tenant's slug as well as its id, like the other tenant endpoints.
- OpenAPI: `read_only` of tenants and the three fields of `TenantExpanded` are marked required (they are always

  spaces.
- Security: `GET /api/v1/auth/support-grants` and `DELETE /api/v1/auth/support-grants/{id}` checked only the

  (`403 auth.support_platform_only`).
- Adding a passkey failed on authenticators without the `credProtect` extension (the server required it): it is now
  asked for but not enforced. Signing in with a passkey still always verifies the user.
- `GET /api/v1/kernel/modules/{name}` answered 500 for modules with data upgrades (`auth`, `webhooks`).

- Lists of one tenant ordered by id (audit entries, users, roles, media, content entries, terms, authors, redirects,
  comments, bans, reports, forms, newsletter lists, subscribers, campaigns, suppressions, webhook endpoints, menus)
  have an index on `(tenant_id, id)`; without it SQLite read and sorted every row of the tenant (the audit list was

- `./gate.sh` ran `cargo xtask api-diff` and `cargo xtask sdk --check` before it stopped on errors, so a

- `catalog`: the OpenAPI schema of an attribute `value` now allows any JSON value (text, number,

- `auth`: a tenant split off a guarded tenant gets the guardrails in the same step that opens it, so it never serves
  a request without them.

## [0.6.0] - 2026-11-12

### Changed

- **Breaking:** `POST /api/v1/auth/me/mfa/totp` (start two-step sign-in) needs
  `{"current_password": "…"}`, like adding a passkey or an API key: a stolen access token alone
  can no longer tie someone else's authenticator app to the account.

### Fixed

- Jobs: the worker no longer waits for a whole batch before taking new jobs: each module runs up
  to `AUTOXIDE_JOBS_CONCURRENCY` jobs at once and a slow job (AI call, slow webhook) only holds
  its own slot. A job whose handler panics counts as a failed attempt; a job whose process died
  on its last attempt goes to the dead-letter queue instead of being retried forever.
- Jobs queued with a `unique_key` that already exists inside a transaction no longer break that
  transaction on Postgres.
- Events: a subscriber that panics or takes longer than 50 seconds counts as a failed delivery
  (retried later) instead of stopping event delivery; an unreadable event row is marked failed
  instead of blocking every later event; a claim is taken with the current time, so a slow
  batch can no longer let a second server deliver the same event.
- Files: an upload cut off midway (timeout, client gone) aborts the partial S3 multipart upload;
  a download the client already has (`If-None-Match`) answers 304 without reading the stored
  content.
- Content: several entries created at the same moment with the same title (automatic slug) no
  longer fail with `content.slug_taken` on Postgres.
- Faster cleanup and filtering: the hourly sign-in cleanup uses indexes and deletes in batches of
  1,000 rows; the audit log filters by `module` through an index (new migrations in `auth` and
  `audit`, applied by `autoxide migrate`).

### Security

- Resetting or changing a password also ends, in the same transaction, everything opened with
  the old password: a pending email change (its confirmation link stops working), a passkey
  registration not finished yet, and a sign-in waiting for its two-step code. A reset also removes
  passkeys and API keys in that same transaction.
- A session or API key is granted only if the password just checked is still the current one
  and the account is still active: a password reset that lands between the check and the grant
  wins.
- Confirming a new email address voids password-reset mails sent to the old one.
- Disabling or deleting a user while someone changes their roles no longer risks a deadlock on
  Postgres.
- Requests whose client address is an IPv4 address written as IPv6 (`::ffff:a.b.c.d`, when the
  server listens on `[::]`) are rate-limited per address again, instead of all sharing one
  limit.
- `Idempotency-Key`: a temporary refusal (429, 408) is no longer stored and replayed; a request
  that timed out or crashed after it may have taken effect answers a retry with
  `409 idempotency_result_unknown` instead of running again; responses over 256 KiB are not
  stored (`409 idempotency_result_too_large` on a retry); `If-Match` is part of the request's
  fingerprint and `ETag` is replayed.
- The NUL character (`\u0000` in JSON, `%00` in a URL) is refused everywhere with
  `400 invalid_character`; before, Postgres answered 500 while SQLite stored it.
- `/health/ready` asks the database at most once a second, however often it is called.
- The `method` label of HTTP metrics only takes standard methods (others count as `other`).
- Webhooks: creating an endpoint and rotating its secret answer with `Cache-Control: no-store`;
  events about endpoints carry only the origin of the URL (paths and queries often hold
  tokens); more IPv6 forms that embed private IPv4 addresses (6to4, IPv4-compatible) and the
  remaining special ranges are refused as targets.
- Files: names with invisible formatting characters (such as right-to-left override) are
  refused.
- Mail: only a permanent SMTP refusal that blames the recipient address (enhanced status
  `5.1.x` / `5.2.x`) emits `mail.delivery_failed`; other permanent errors (wrong SMTP password,
  sender not allowed, sending quota) are retried and then land in the dead-letter queue, so a
  misconfigured SMTP server no longer gets every newsletter subscriber blocked.
- Backups and the scratch copy made during a restore are created readable by their owner only
  (`0700` directories, on Unix).

  and email change, login throttling, rate limiting.
- Events and an append-only audit log; a job queue stored in the database with retries,
  schedules and a dead-letter queue.
- Error messages in English and Vietnamese; idempotency keys for safe retries.
- Mail over SMTP (or files during development); file storage on local disk or S3 with
  size and type limits.
- An MCP endpoint (`/mcp`) so AI agents can call the system as tools, with the caller's
  permissions.
- A sample module (`notes`) and a guide for writing modules.
- Tooling: `autoxide copy` between SQLite and PostgreSQL, `autoxide backup` and
  `autoxide restore`, benchmarks and a load test, Docker image and Compose file, CI.
