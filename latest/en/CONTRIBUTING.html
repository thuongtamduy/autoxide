Autoxide documentation v0.20.0

Contributing to Autoxide

English · Tiếng Việt

Thank you for helping. This guide is for people; if you work with an AI coding agent, point it at AGENTS.md (short, in English; the full internal rules are in CLAUDE.md), which holds the rules the agent follows. The rules below are the same, only shorter. Everyone taking part follows the code of conduct.

Before you start

  • Bugs: open an issue with the version, the database (SQLite or PostgreSQL) and the steps that reproduce it.
  • Security problems: do not open an issue; follow SECURITY.md.
  • New features: open an issue first and describe the problem you want to solve. The core stays neutral about business domains (no orders, stock or patients in the core — those belong in modules), and the order of work follows docs/ROADMAP.md, so a short discussion saves you from writing code that cannot be merged.

Set up your machine

You need:

  • Rust — rustup installs the exact toolchain pinned in rust-toolchain.toml the first time you run cargo;
  • a C compiler (SQLite is compiled from source);
  • Docker, for the PostgreSQL and S3 tests of the full gate;
  • cargo-deny: cargo install cargo-deny --locked;
  • optionally gitleaks (the gate runs it in Docker otherwise).

On a fresh Linux x86_64 machine (for example a cloud agent session) run scripts/cloud-setup.sh instead of installing by hand: it installs the pinned toolchain and cargo-deny, gitleaks and cargo-nextest from prebuilt releases, checking pinned SHA-256 checksums. It is safe to run again.

Then:

git clone https://github.com/thuongtamduy/autoxide.git autoxide
cd autoxide
git config core.hooksPath .githooks
cargo test --workspace

The Git hooks check formatting and scan staged changes for secrets before each commit.

Check your change: two gates

The gate is the definition of “done”. There are two levels:

./gate.sh --quick

While you work, before each commit: formatting, lints, boundary checks, dependencies, secrets, and the tests of the crates you changed (and of the crates that depend on them), on SQLite only. It needs no Docker for the tests and usually takes a minute or two.

./gate.sh

Before you open a pull request: everything above, and every test on both SQLite and PostgreSQL (the gate starts throwaway Docker containers). A change is merged only when this gate is green.

When the gate is red, fix the code. Do not loosen the gate, turn off a lint or skip a test.

A change that only touches files listed in scripts/rust-free-paths.txt (documentation, the TypeScript SDK, changelog fragments, decisions) cannot change any Rust result: --quick skips Clippy for it, and on a pull request CI skips the Rust build and tests (the jobs still report success). Anything not in that list runs everything.

The rules that matter most

  • Both databases. Everything that touches the database — migrations, queries, transactions, indexes, tests — must work on SQLite and PostgreSQL. A feature that works on one only is not finished. Do not use types, functions or syntax only one of them has.
  • Module boundaries. Each module is its own crate under modules/ and owns its tables (named <module>_…). A module never reads, writes or joins another module’s tables and never has foreign keys to them; it calls other modules only through the traits they publish in pub mod api. cargo xtask check (part of the gate) enforces this.
  • Logic in services. HTTP handlers and MCP tools only take input, call a service and return the response; REST and MCP share the same service.
  • Errors have a stable code. Every error returned to clients is an autoxide_kernel::error::Error with a snake_case code (module errors start with <module>.) and a message that says what to fix. The code is a contract with clients: changing it is a breaking change. Each new code needs a Vietnamese translation in the crate’s locales/vi.json.
  • The API contract stays in sync. Every route is documented in OpenAPI. When you change the API or a setting, run cargo xtask regen: it regenerates every generated file in one go (docs/openapi.json, docs/mcp-tools.json, .env.example, the TypeScript SDK schema). The the gate on your machine checks them early (cargo xtask regen --check) and prints this command when one is stale (this step runs only locally; on CI the tests that keep the documents in sync with the code check them). Never change the behaviour of an existing /api/v1 endpoint in a breaking way; add a new one and deprecate the old.
  • Tests. New code comes with tests. Tests that touch the database use autoxide_testkit::TestDatabase, which gives each test an empty database on whichever of SQLite or PostgreSQL the gate is running.
  • No unsafe, no unwrap / expect / panic! outside tests. Return an error instead.
  • No secrets in Git. Only .env.example is committed, never .env.
  • Documentation in two languages. User-facing documents (README, guides in docs/, this file) have an English version and a Vietnamese one (*.vi.md) with the same content: change both in the same commit. Internal documents (CLAUDE.md, STACK.md, docs/ROADMAP.md, docs/DECISIONS.md) and code comments may be in Vietnamese.

The full list, with the reasons behind each rule, is in CLAUDE.md; past decisions are indexed by topic in docs/decisions/INDEX.md, which is generated and not committed: run cargo xtask decisions to create it.

Commits and pull requests

  • Keep a pull request to one change. Split unrelated changes.
  • For anything a user of Autoxide would notice, add a small file to changelog.d/ instead of editing CHANGELOG.md: name it <name>.<section>.md (added, changed, deprecated, removed, fixed or security) and write the English bullet points as they will appear in the changelog. They are folded into CHANGELOG.md at release time, so parallel pull requests never conflict there.
  • In the pull request, say what you changed, why, and confirm that ./gate.sh --quick is green (CI runs the rest, including PostgreSQL; the full ./gate.sh is required before a release).

Commit messages

Commit messages follow a light form of Conventional Commits:

<type>(<scope>): <short summary in the imperative mood, at most 72 characters>

<optional body: why the change is needed, what you considered, what it does not do>

Signed-off-by: Your Name <you@example.com>
  • type is one of feat, fix, docs, refactor, perf, test, build, ci, chore, revert. scope is optional: a module or crate name (orders, kernel).
  • Mark a breaking change with ! after the scope (feat(kernel)!: …) and explain it in the body. Breaking changes of the stable contract tier follow docs/COMPATIBILITY.md.
  • Write in English or Vietnamese. Explain why in the body when it is not obvious.
  • The pull request title is used as the squash-merge subject, so it follows the same form.

Sign your commits (DCO)

Autoxide uses the Developer Certificate of Origin (DCO) instead of a contributor license agreement. By adding a Signed-off-by line you certify that you wrote the change or have the right to submit it under the project license. Add it with -s:

git commit -s -m "fix(notes): reject empty titles"

To sign commits you already made: git rebase --signoff origin/main and push again with --force-with-lease. The DCO sign-off job in CI fails when a commit of a pull request has no Signed-off-by line (when the branch the pull request targets has no .github/CODEOWNERS yet, which is true of old branches such as a release/X.Y cut from an old tag, nothing is checked; merge commits are not checked, so prefer rebasing over merging main into your branch). A pull request opened by a maintainer (a login listed in .github/CODEOWNERS on the branch the pull request targets, not in the pull request; GitHub authenticates the login) is exempt, including commits written by their agent sessions: maintainers are the licensors and answer for what they submit.

Contributions written with AI assistance

Autoxide is itself built with AI agents (CLAUDE.md), so AI-assisted contributions are welcome. The rules exist to keep a person accountable and the review load fair:

  • Say so. Tell us in the pull request description which tool helped and for what. Add a trailer such as Assisted-by: <tool or model> to the commit if the tool wrote a substantial part.
  • A person is responsible. The Signed-off-by line is yours, not the tool’s. You have read every line, you understand it and can explain it in review, and you ran ./gate.sh --quick yourself.
  • Check what the tool made up. Confirm every dependency, function and API exists in the pinned version (the repository’s check-library-api skill shows how). Remove invented references, and never paste secrets, personal data or customer data into a tool.
  • Do not send what you cannot defend. Unreviewed bulk output, many unrelated changes in one pull request, or replies to review comments that are pasted tool output may be closed without a detailed review.
  • Licensing. Do not submit output that you know copies code under an incompatible license.

Labels and where to start

Maintainers label issues so newcomers can find a first task: good first issue (small, well described, a maintainer will help), help wanted (we would like a contribution, any size) and the rest listed in GOVERNANCE.md. Comment on an issue before you start so two people do not do the same work.
