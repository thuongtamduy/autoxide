Autoxide documentation v0.20.0

RC trial, round 1 (AI agents playing users)

English · Tiếng Việt

Important: the testers were AI agents playing a role, not people. Round 1 ran on main at version 0.19.0 (before 1.0.0-rc.1), as an early check (the project owner asked AI agents to play users before outside testers, in a few rounds). Every tester saw only public documents (README, docs/guides, docs/*.md, OpenAPI, examples/), never the source of crates/ or modules/ (the module-author role could also read modules/<name>/src/api.rs). Subagents: the newcomer role ran on a small model (to imitate a less experienced person), the other four on a mid-size model. No real secret and no real provider or AI model was used.

Environment limits that shaped the results (not product bugs): 4 CPU cores, no Docker daemon (the Docker quickstart was not tried), so every role used the binary, with SQLite or a local PostgreSQL 16. The binary was built once up front (cargo build -p autoxide, debug, 10 min 06 s on a cold cache); roles timed themselves from “binary exists”. Timings below come from the agents’ own clocks and are approximate where stated.

Role 2 — Module author outside the repository

Goal: follow docs/guides/writing-a-module.md, make a small module in a directory outside the repo, run check-module, test on SQLite and PostgreSQL. Result: reached. The module links was generated with cargo xtask new-module --external … links link --core-path … (the guide’s way); it is a renamed copy of the sample, the tester did not write new business logic. check-module: no violations. Tests: 8 + 4 pass on SQLite and on PostgreSQL (port 15432). POST / GET /api/v1/links work, a duplicate gives 409 links.url_taken.

Time: generate 0:23; first server build 32:08 (compile wait, slowed by a stray build); binary to a working endpoint about 1:00; check-module 1 s when the machine is free; SQLite tests 6:41 (rebuild after a machine restart), PostgreSQL 10 s.

Role 4 — Operator

Goal: set up with PostgreSQL 16 (no Docker daemon), migrate, doctor, metrics, backup, restore, graceful stop, upgrade. Result: reached (4 min 16 s). All documented commands that could run did what the docs say. Restore: 460 tables, row counts match (apart from rows the tester added by logging in), the old admin password works, 3355 address units and 8 tax rates are intact. Not tried (no Docker, out of scope): docker compose / docker run, gh attestation verify, systemd, SQLite→PostgreSQL copy, multi-tenant, OTLP, encrypted backup / PITR.

Upgrade: no earlier release to upgrade from. Simulated the documented module on/off path: serve warns modules_turned_off, doctor warns, autoxide modules says “1 table(s) with rows”, backup refuses with instructions; migrate down customers then up is clean.

Role 5 — Shop owner using the API (curl and the TypeScript SDK)

Goal: customer, product, stock, promotion, order, simulated payment, draft e-invoice. Result: partly reached. The whole sale flow ran with curl and with the SDK; money checked by hand (300,000; 480,000 with tax 43,636; 210,000 with tax 19,091), integer strings plus VND; four buyers in parallel for the last item gave exactly one order; partial refund, cancel of a paid order and refund replays did not double. About 15 min (estimate); about 6.5 min of it was looking for steps the guide lacks. The SDK runs directly with Node 22, no npm install.

Real bugs:

  • L1 (most serious): stock on_hand never goes down after delivery. Sandbox tenant, one variant with 10 in stock, order 2, pay (notification), create a shipment, POST /shipping/shipments/{id}/status through ready_to_ship, picked_up, in_transit, delivered (or POST /orders/{id}/transitions to preparing, shipping, delivered). Seen after waiting 20 s: order delivered, but GET /inventory/levels shows on_hand 10, available 8, reserved 2; GET /inventory/movements has only the +10 adjustment, no sale; the reservation stays confirmed; the order’s fulfillment_status stays unfulfilled. Expected (INVENTORY.md, Reservations: “fulfil — writes sale lines”): sale −2, on_hand 8, reserved 0, fulfilled. available is right, so no overselling, but the ledger of stock is wrong.
  • L2: payment_actions[].payment_id from checkout (and from POST /orders/{id}/payment-link) is not the ledger payment id: GET /ledger/payments/{id} returns 404 ledger.payment_not_found; the real id appears only in GET /ledger/payments (filter source_id).
  • L3 (small): repeating checkout, or cancelling a guest order, with the same Idempotency-Key returns 200 (first call 201) without the Idempotent-Replayed: true header, unlike retries.md and the OpenAPI text.
  • L4 (small): POST /orders/{id}/payment-link after a failed first payment returns the first (failed) payment_id and status_token; that token stays pending while the ledger has a new payment with another id.
  • L5 (small): a MoMo notification with the wrong amount sets needs_review (as documented); a correct notification sent afterwards does not bring it to succeeded and the order stays pending_payment; nothing says how an operator clears it.

Summary by priority

  1. Blocking for 1.0: UT-1 (stock never decreases on delivery), UT-2 (API-key scope problem over MCP, details withheld).
  2. Annoying, fix before the RC feedback window: UT-3 (fastest path without Docker: binary, secrets, migrate up, port, PostgreSQL), UT-4 (no way to try a sale without real providers; shop guide missing steps), UT-5 (MCP tools: missing parameter descriptions, price lists / customers, validation of values), UT-6 (payment ids, idempotency headers, payment-link replay), UT-7 (first build time of a module outside the repo).
  3. Small: UT-8 (messages and logs for operators), UT-9 (rate-limit docs vs behaviour, internal id in public data).

Note: the first-build time of a module (about 30 min) puts G9’s “first module under 30 minutes” at risk.

Housekeeping: a second build left running by role 1 competed with role 2 for CPU for most of its wait; it could not be stopped from this session. Files left in /tmp of the trial machine only; nothing was changed in the product code. Role 4 and role 2 left a local PostgreSQL running (ports 15434 and 15432).
