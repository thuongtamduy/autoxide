## D-20261121-scim · Bước 66: SCIM 2.0 trong `auth` — token riêng của khách, endpoint theo chuẩn SCIM thay cho envelope chung, mức lọc và PATCH, không Bulk — 2026-11-21 — agent quyết

Chủ đề: Xác thực, phân quyền, bảo mật

Quyết định:

1. **Đường dẫn:** endpoint SCIM ở `/api/v1/auth/scim/v2/` (`Users`, `Groups`, `ServiceProviderConfig`,
   `ResourceTypes`, `Schemas`), không phải `/scim/v2/{tenant}/` của đặc tả. Khách lấy từ chính token SCIM
   (`axscim1_<ID khách>_<ngẫu nhiên>`, như API key — D-285), nên đường dẫn không cần ID khách; route nằm trong module
   `auth` như mọi route khác, không cần kernel gắn route ngoài `/api/v1/<module>`. Entra ID, Okta, Google Workspace
   nhận bất kỳ URL gốc nào. Header `Autoxide-Tenant` / tên miền không đổi được khách của token.
2. **Token SCIM là bảng riêng** `auth_scim_tokens`, không phải dòng `auth_api_key` loại `scim` như đặc tả gợi ý: API key
   gắn với một người và quyền của người đó, token SCIM gắn với khách. Bảng riêng thì bộ xác thực chung không bao giờ
   nhận token SCIM (không phải API key, không phải access token → 401), và endpoint SCIM không nhận access token / API
   key. Chỉ lưu SHA-256; tối đa 5 token mỗi khách; xoay vòng = tạo mới, đổi ở hệ thống danh tính, thu hồi cũ. Quản lý
   qua `GET/POST /api/v1/auth/scim/tokens`, `DELETE /api/v1/auth/scim/tokens/{id}`, permission `auth.scim.manage`
   (rủi ro `destructive`), tính năng gói `auth.scim` (kiểm khi tạo token và ở mỗi request SCIM).
3. **Lệch envelope chung có chủ đích** (chuẩn ngành thắng ở endpoint SCIM, vì client là Entra ID / Okta chứ không
   phải client của Autoxide):
   - thân `application/scim+json` (nhận cả `application/json`), đọc bằng `Bytes` + `serde_json` thay vì `ValidJson`
     (`ValidJson` chỉ nhận `application/json`, lỗi của nó là Problem);
   - danh sách là `ListResponse` (`totalResults`, `startIndex`, `itemsPerPage`, `Resources`), phân trang
     `startIndex` / `count` bằng `OFFSET` (chuẩn chỉ có phân trang theo chỉ số; danh sách nhân viên một khách nhỏ,
     sắp theo ID UUIDv7 nên ổn định) — ngoại lệ với luật "danh sách bằng `fetch_page`";
   - lỗi theo `urn:ietf:params:scim:api:messages:2.0:Error` (`status` là chuỗi, `scimType`), không phải Problem;
     `detail` chỉ tiếng Anh (máy đọc máy). Kernel thêm `autoxide_kernel::http::StandardErrorBody`: response mang
     extension này giữ nguyên thân lỗi, lớp chuẩn hoá lỗi không đổi nó thành Problem (cộng thêm, không phá vỡ);
   - ba endpoint khám phá không cần token (RFC 7644 §4), nội dung cố định.
   Endpoint quản trị token và luật ánh xạ vẫn dùng envelope chung.
4. **Mức lọc:** `eq`, `ne`, `co`, `sw`, `ew`, `pr`, nối `and` / `or`, ngoặc. Không `not`, `gt`/`ge`/`lt`/`le`, không bộ
   lọc giá trị `attr[…]` ở tham số `filter` (gặp thì `invalidFilter`). `User` lọc được theo `userName`, `externalId`,
   `emails` (`emails.value`), `active`, `id`; `Group` theo `displayName`, `externalId`, `id`, `members` (`eq`).
   So chuỗi không phân biệt hoa thường, trừ `externalId eq` (caseExact theo RFC 7643). Để hai database cho cùng kết
   quả, cột so được lưu thêm bản chữ thường (`user_name_key`, `external_key`, `display_name_key`), mẫu `LIKE` thoát
   `%`, `_`. `sort`, `etag`, `changePassword` không hỗ trợ (`ServiceProviderConfig` nói rõ).
5. **Không `Bulk`** ở bản đầu (đặc tả khuyến nghị): Entra ID, Okta, Google không cần nó.
6. **PATCH (RFC 7644 §3.5.2)** áp lên bản JSON của tài nguyên rồi đọc lại như `PUT` — một cách cho mọi thuộc tính.
   Tương thích Entra ID / Okta: `op` không phân biệt hoa thường, giá trị `"True"`/`"False"` dạng chuỗi, `value` object
   không `path` (kể cả khoá `name.givenName`), `remove` `members` kèm `value` mảng, đặt `emails[type eq "work"].value`
   khi chưa có phần tử khớp thì thêm phần tử. Thuộc tính Autoxide không lưu (lược đồ mở rộng enterprise, `title`, số
   điện thoại…) bị bỏ qua.
7. **Ánh xạ `User`:** tài khoản nhân sự (`realm = staff`) của khách; liên kết ở `auth_scim_users` (khoá = ID tài
   khoản; `userName` unique không phân biệt hoa thường, `externalId` unique). Email lấy từ `emails` (`primary`, không
   thì phần tử đầu), không có thì `userName` nếu là email. Tên hiển thị: `displayName` → `name.formatted` → tên riêng +
   họ → `userName`. Tài khoản tạo qua SCIM không có mật khẩu (đăng nhập qua OIDC của khách hay đặt mật khẩu bằng link)
   và email coi là đã xác minh: hệ thống danh tính của khách là nguồn của email nhân viên. `POST` với email của tài
   khoản nhân sự có sẵn chưa liên kết SCIM thì **nhận** tài khoản đó (khách bật SCIM sau khi đã có nhân viên) thay vì
   báo trùng. Mật khẩu, MFA, passkey không bao giờ bị SCIM ghi.
8. **`active = false`** → trong CÙNG transaction (sau khi khoá dòng tài khoản, D-181): `disabled_at`, thu hồi mọi phiên /
   refresh token (`SessionService::revoke_user`) và API key (`revoke_all_in`, mỗi key một event), event
   `auth.user_updated`. Access token đang cầm bị từ chối ở request kế (bộ xác thực kiểm tài khoản còn hoạt động). Không
   khoá được admin cuối cùng (409). Bật lại không hồi sinh API key. Event của SCIM ghi `actor_kind = scim`.
9. **`DELETE`** dùng quy trình xoá tài khoản sẵn có (`UserService::delete`: event `auth.user_deleted` để module khác
   xoá phần của họ); liên kết SCIM xoá cùng transaction. Muốn chỉ chặn truy cập thì hệ thống danh tính PATCH
   `active=false` — cách Entra ID và Okta làm mặc định.

Lý do: tiêu chí "tiêu chuẩn" — client SCIM chỉ hiểu đúng RFC 7643/7644; giữ phần quản trị trong envelope chung để học
một endpoint là biết các endpoint còn lại. Token theo khách và tách khỏi API key để token lộ không mở được API khác.

Căn cứ: RFC 7643, RFC 7644 (SCIM 2.0). Dữ liệu nhân viên xử lý theo Luật Bảo vệ dữ liệu cá nhân 91/2025/QH15 (hiệu lực
01/01/2026): khách là bên kiểm soát dữ liệu, Autoxide là bên xử lý theo chỉ dẫn của khách — cần đối chiếu văn bản gốc /
người có chuyên môn pháp lý.

Đã cân nhắc:
- Token là API key loại `scim`: tái dùng xoay vòng của API key, nhưng key phải có chủ là một người (quyền = quyền của
  chủ ∩ quyền key) và bộ xác thực chung phải thêm nhánh chặn — loại.
- Envelope Problem / `cursor` cho endpoint SCIM: Entra ID và Okta không đọc được — loại.
- Gắn route `/scim/v2/{tenant}` ở gốc máy chủ: cần hàm mới của kernel cho route ngoài `/api/v1`, không thêm gì cho
  client — loại.

Thay: phần "token SCIM là loại API key `scim`" và đường dẫn `/scim/v2/{tenant}/` của đặc tả bước 66 (D-221 giao bước).
