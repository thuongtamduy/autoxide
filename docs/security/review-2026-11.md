# Security review, November 2026 (pre-1.0)

> **What this is:** an internal review by the maintainers, carried out with AI assistance (several
> AI agents each reviewing one area of the code independently, then every finding checked again
> against the code or with a test). **It is not an audit by an independent third party**, and it
> does not certify that Autoxide is free of vulnerabilities. To report a problem, see
> [`SECURITY.md`](../../SECURITY.md).

- **Date:** 2026-11-23
- **Version reviewed:** `main` after the 0.x releases of November 2026 (commit `9411c6f`), before 1.0
- **Roadmap item:** step 70, P6

## Scope

The whole repository: the kernel (`crates/kernel`), the binary (`crates/app`), every module under
`modules/`, the developer tooling (`xtask`), the GitHub Actions workflows and the container image.
The review looked at the code paths an attacker can reach over HTTP (REST, MCP, the event stream,
inbound webhooks) and at the background jobs those requests start.

It was split into six areas, each reviewed separately:

| Area | What was covered |
| ---- | ---------------- |
| Authentication | password login and throttling, password hashing, reset / verification / sign-in-link tokens, access and refresh tokens, API keys, TOTP and recovery codes, passkeys, OpenID Connect, step-up (re-confirmation), invitations, account lockout and deletion |
| Authorization and tenant isolation | how the tenant of a request is chosen, delegation to child tenants, support access, scoped permissions, the `tenant-scope` gate, cross-tenant and cross-organization access in every module that holds business data |
| MCP, event stream, outbound webhooks, automations, AI | parity between MCP tools and REST endpoints, SSE / WebSocket filtering, server-side request forgery in outbound calls, the principal automations run as, AI output handling |
| Money and providers | payment, bank-feed and carrier webhooks (signatures, replay, tenant routing), encryption of provider credentials, ledger, refunds, orders, promotions, inventory, idempotency, races |
| Uploads, outbound requests, templates | file and media storage, content types, image decoding, presigned uploads, the shared address filter for outbound requests, tenant templates, user content rendering, CSV import and export, input limits |
| HTTP layer, configuration, personal data, supply chain | security headers, CORS, body and time limits, rate limiting and client addresses, error responses, logging, defaults and `autoxide doctor`, personal data export and deletion, CI workflows, the Dockerfile, dependency checks |

## Method

1. Each area was read by a separate AI agent that had the project rules ([`CLAUDE.md`](../../CLAUDE.md))
   and the earlier hardening decisions, and was asked to look for what the existing gates and tests do
   not catch. Agents did not edit code.
2. Every finding they reported was checked again by reading the code path end to end (route →
   handler → service → query). Findings that could not be confirmed are listed as such.
3. Each confirmed high or medium finding was fixed with a regression test that fails before the fix
   and runs on both SQLite and PostgreSQL. Where a whole class of bug could be caught by tooling, the
   tooling was fixed too.

Automated checks that already run on every change and were not repeated here: `cargo deny`
(RustSec advisories, licenses, sources), `gitleaks`, `clippy` with warnings as errors, and the
project's own `cargo xtask check` rules (`tenant-scope`, `mcp-principal`, module boundaries).

## Severity

- **High:** lets an attacker act on data or money that is not theirs, or take over an account,
  under realistic conditions.
- **Medium:** a real weakness that needs an extra condition (a specific permission, a configuration,
  a race) or affects integrity or privacy without a direct takeover.
- **Low / informational:** defence in depth, hardening, or documentation.

## Findings fixed in this review

| ID | Severity | Area | Finding | Fix |
| -- | -------- | ---- | ------- | --- |
| H-1 | High | `shipping` | A carrier webhook updated any shipment of the tenant with a matching tracking number, not only shipments booked through the carrier account that received the webhook. In a tenant with several sellers or organizations, one seller could change another seller's shipment status with their own webhook. | Webhook updates only match shipments (and parcels) booked through the receiving carrier account. |
| H-2 | High | `auth` | The "this wasn't me" lockout after an email change did not remove external sign-in links or revoke pending sign-in-link and re-confirmation tokens, so the person who changed the email could get back in. | The lockout removes them, like a password recovery does. |
| H-3 | High | `auth` | `AUTOXIDE_AUTH_TOKEN_SECRET` accepted the example value from `.env.example`; a server started with it signs access tokens with a public key. | The example value is refused at startup (also for `…_PREVIOUS`), like `AUTOXIDE_SECRET_KEY`. |
| M-1 | Medium | `ledger` | A bank credit settled a VietQR payment by the transfer code alone, even when the money arrived in a different bank account (for example another seller's) than the payment expected. | The credit must arrive in the payment's bank account; otherwise it goes to the reconciliation queue. |
| M-2 | Medium | `ledger` | Two concurrent "match" resolutions of one reconciliation item could settle two payments with one credit. | The item is claimed with a conditional update before the payment is settled. |
| M-3 | Medium | `automations` | Saving or enabling a rule, and approving a step, did not require the re-confirmation (step-up) that the same `money` / `destructive` action requires over REST, so a stale session could schedule such an action. | Saving, editing, enabling and approving check the tool exactly like REST, including step-up. |
| M-4 | Medium | `auth` | A role marked "requires two-step sign-in" was skipped in the user's own tenant when they had no second factor, but still applied when they entered a child tenant through a delegation or used a support grant. | Delegation and support access apply the same rule. |
| M-5 | Medium | HTTP server | The server had no timeout for reading request headers, so slow clients could hold connections open indefinitely. | Headers must arrive within 30 seconds; idle HTTP/2 connections are pinged. |
| M-6 | Medium | `xtask` | The `tenant-scope` gate did not see entities declared through a module-local `tenant_scoped!()` macro, so eleven modules (including `ledger`, `catalog`, `inventory`, `promotions`, `shipping`) were not checked for queries that forget the tenant filter. No exploitable query was found in them. | The gate understands the macro; the existing calls it now reports were scoped or annotated. |
| M-8 | Medium | `auth` | "Requires two-step sign-in" on a role checked that the account *had* a second factor, but password sign-in only asks for an authenticator-app code; an account whose only second factor was a passkey could sign in with the password alone and get the role's permissions. | Such an account must sign in with its passkey; password, sign-in link and external sign-in are refused (`auth.passkey_required`). |
| M-7 | Medium | `bookings`, `inventory`, `orders` | Bookings, restock alerts and orders were left out of the personal data export, and deleting an account left the customer's name, phone and email in bookings and restock alerts. | The three modules register their personal data; bookings and restock alerts handle account deletion (orders are kept as accounting records). |
| L-1 | Low | `automations` | A rule triggered by an event did not require the permission to stream that event, unlike webhooks; the event payload is readable in the run. | Saving such a rule requires the event's stream permission. |
| L-2 | Low | `plans` | The MCP tool `change_subscription` did not refuse a subscription billed through an app store, unlike the REST endpoint. | The tool applies the same check. |
| L-3 | Low | kernel | `GET /api/v1/kernel/find` had no maximum length for `q`. | `q` is limited to 200 characters. |
| L-4 | Low | kernel | The HTTP client for tenant-chosen connector addresses used the system proxy, which resolves names itself and so bypassed the public-address filter. No connector uses tenant-chosen addresses yet. | The client ignores the system proxy. |
| L-5 | Low | docs | `SECURITY.md` said the server warns about rate limiting being off, `CORS_ORIGINS=*` and `/metrics` on the public port, but it did not. | The three startup warnings were added. |
| L-6 | Low | `ledger` | After a short payment was accepted as received, the refund limit was the expected amount, not the amount received. | Payments store the amount captured; refunds are limited to it. |
| I-1 | Info | `ledger` | A refund notification was matched by the provider's reference without checking the provider. | The refund's payment must have gone through the provider that sent the notification. |
| I-3 | Info | `invoices` | The printable invoice HTML relied on the global security headers (which an operator can turn off) for its sandbox. | The response sets its own sandbox CSP. |
| I-4 | Info | `app` | The first administrator's email was written to the startup log. | The log names the user ID. |

## Findings fixed after the review

Low and informational findings first left open, fixed later by the maintainers with AI assistance in the
same way (each fix with a test that fails without it, and a changelog entry under **Security**).

| ID | Severity | Area | Finding | Fix |
| -- | -------- | ---- | ------- | --- |
| L-9 | Low | kernel | The API documentation page's CSP allowed any script from the CDN, not only the pinned Scalar bundle. | The CSP allows only the pinned script file; styles and fonts no longer come from the CDN. Checked in Chromium: the page renders with no CSP error of its own (#505). |
| L-10 | Low | HTTP server | There was no cap on the number of open connections, and a connection that never sent a byte was not closed by the header timeout. | `AUTOXIDE_HTTP_MAX_CONNECTIONS` (default 4096): over it new connections wait in the operating system's queue rather than being refused; a silent connection is closed after 30 seconds (#505). Open WebSockets count towards the limit, a silent connection no longer delays a graceful shutdown, and the server warns when the limit is not below `ulimit -n` (#512). |
| I-2 | Info | kernel, `ai` | Responses from operator-configured providers were read without a size cap. | Read up to `AUTOXIDE_PROVIDER_MAX_RESPONSE_BYTES` (default 16 MiB); a larger answer fails the call (#505). |
| I-5 | Info | CI | The `gitleaks` container image was pinned by tag, not digest. | Pinned by digest in `.github/gitleaks/Dockerfile`, read by both CI and `gate.sh`, updated by Dependabot (#505). |
| L-7 | Low | `auth` | Changing the password (not recovering it) kept existing API keys, passkeys and external sign-in links. | `POST /api/v1/auth/me/password` takes `revoke_other_credentials`; `true` removes them in the same transaction, as a password recovery does. Without it they keep working, as documented on the endpoint (#508). |
| L-8 | Low | `automations` | Event-triggered rules started for events of every organization in the tenant, not only the rule's organization. | Events carry their organization one uniform way (`org_id` of the payload, or of its `after` / `before` snapshot, read by `Delivered::org_id()`). A rule of a unit below the root starts only for events of that unit's branch; events naming no unit reach only tenant-wide rules (#512). |

## What was checked and found sound

A summary, so later reviews know what was covered:

- **Tokens and sessions:** access tokens accept only HS256 with a per-tenant derived key and are
  checked against a live session; refresh tokens rotate with reuse detection; one-time tokens are
  hashed, purpose- and tenant-scoped and consumed atomically; TOTP codes cannot be replayed; passkey
  ceremonies are single-use and bound to the user; OpenID Connect uses single-use state, nonce and
  PKCE, and only links accounts when both sides are verified.
- **Tenant choice:** the tenant comes from the credential; a header naming another tenant is only
  honoured through a delegation or a time-limited support grant; delegations are only granted to
  descendants.
- **Inbound webhooks:** payment, bank-feed and carrier webhooks resolve the tenant from an HMAC-derived
  address before checking signatures, compare secrets in constant time, deduplicate deliveries and
  check amount and currency against the stored payment.
- **Money:** prices come from the catalog with checked arithmetic; refunds, stored value, promotion
  usage and stock reservations use atomic, bounded updates; provider credentials are sealed with
  AES-256-GCM bound to tenant and row.
- **Outbound requests:** the shared address filter blocks private, loopback, link-local and
  reserved ranges including IPv4 embedded in IPv6, filters at connect time (no DNS rebinding) and
  disables redirects.
- **Files and templates:** storage keys are server-generated and tenant-prefixed; size limits are
  enforced while streaming; files are served as attachments with `nosniff` and a sandbox CSP;
  templates have no loader, no raw-HTML filter, and fuel and recursion limits.
- **MCP and event stream:** MCP reuses the REST authentication and re-checks each tool call, including
  step-up; the event stream filters by tenant, permission and reach.
- **CI and supply chain:** actions pinned by commit, least-privilege token permissions, no
  `pull_request_target`, no untrusted input interpolated into shell steps; the container runs as a
  non-root user from digest-pinned base images; `cargo deny` runs on every pull request and daily.

## Not covered

Areas the review did not reach, or reached only partly, for a later review:

- the SCIM provisioning endpoints and phone-number verification;
- the tenant export, import and move archive formats (path traversal, decompression);
- every MCP tool compared with its REST endpoint (a sample and the `mcp-principal` gate were used);
- loyalty points, referral rewards and point-of-sale tender splits in depth;
- the `content`, `media`, `newsletter` and `analytics` modules beyond spot checks.

## Black-box test

After the code review, the running server was attacked from the outside, without reading the code
first; a finding was confirmed in the code only once it had been reproduced over HTTP. Roadmap item:
step 70, P14.

### Scope and set-up

- **Build:** `cargo build --release -p autoxide` of `main` on 2026-11-23, run with `autoxide serve`.
- **Databases:** one server on SQLite and one on PostgreSQL 16, same configuration.
- **Configuration:** `AUTOXIDE_TENANCY_MODE=multi`, `AUTOXIDE_MODULES=all` (official and experimental
  modules), event stream and metrics on, the general per-address rate limit raised so that scans were not cut
  short (the per-account and per-address limits of sign-in and codes stayed on). Reference data loaded (`address.import`,
  `tax.import_pack`, `promotions.load_legal_data`).
- **Tenants and accounts:** two tenants, A and B, each with an administrator, a staff account holding
  a narrow role (read products, write own content, post comments, upload files), a customer account,
  and API keys of narrow scope. Each tenant had products, prices, stock, content, files, media, forms,
  webhooks, tags, carts and orders.
- **Tools:** `curl`, short Python scripts (standard library only) for HTTP, MCP, Server-Sent Events
  and a minimal WebSocket client. No outside service was attacked; outbound addresses pointed at
  unroutable documentation ranges.

### What was tried

| Area | Tried | Result |
| ---- | ----- | ------ |
| Tenant isolation | Every `GET` path with an id in the OpenAPI document called as A's administrator, staff and customer with each of B's ids (≈2,500 requests); every list endpoint with `limit`, `q` and B's `org_id`; B's ids in record notes, tags, activity, tag merge, bulk actions; `Autoxide-Tenant` set to B's slug, id and the default tenant with A's credentials; A's SCIM token with B's header; A's form token on B; A's order token on B | No data of B was returned or changed. Two settings endpoints keyed by organization (`ledger/flow-settings/{org_id}`, `support/policies/{org_id}`) accept any id and answer with defaults; what is written is stored under the caller's tenant only |
| Privilege escalation | Every `GET` without parameters as staff and as customer; staff and customer on administrative writes; a narrow API key on user, key, password, MFA, session, settings, devtools and tag endpoints over REST and MCP; delegation and support grants towards a tenant that is not a descendant; platform-only endpoints as a tenant administrator | Refused, except: **P-1** (fixed) and **P-3** (fixed) below |
| Authentication | Password guessing (lockout after 5, also for email case and spaces), guessing the current password through key creation, password change and re-confirmation; access and refresh token after logout, password change, disabling the account; refresh token reuse (sequential and 20 concurrent) | All refused as documented; a reused refresh token revokes its family |
| Injection | SQL and template payloads in every query parameter of every list endpoint (`order`, `cursor`, `sort`, `q`, filters), JSON nesting 100,000 deep, malformed JSON | No server error, no database error text, no evaluation |
| Stored XSS | Content bodies with `javascript:`, `data:`, protocol-relative and control-character links, raw HTML nodes; comments in Markdown with scripts and event handlers; SVG with script uploaded to media; HTML uploaded to files | Unsafe links and nodes refused with field errors; comment HTML escaped and links dropped; script-bearing SVG refused; files served as attachments with `nosniff` and a sandbox CSP |
| SSRF | Webhook addresses on loopback, private, link-local, metadata, IPv6-mapped, octal, hexadecimal and decimal IPv4 forms, `file:` and `gopher:` | Refused at save; host names are checked at connect time and the client ignores the system proxy |
| Open redirect | `return_url` of payments | **P-5** (fixed later, low) |
| Races | 20–30 concurrent checkouts for 1–2 items in stock; 15 concurrent checkouts with a promotion code limited to one use; one `Idempotency-Key` reused by another guest, another user, another tenant and with another body | No overselling, one use of the code, keys scoped to their caller; tested on SQLite and PostgreSQL |
| Cheap denial of service | 20 MB body, 200 MB gzip body (`Content-Encoding: gzip`), `limit=100000`, PNGs declaring 60,000 × 60,000 pixels, many SMS codes from one address | Body closed early or refused; compressed bodies are not inflated; images that large get no derived copies; **P-2** (fixed) |
| Information disclosure | Error bodies, response headers, `/metrics`, the OpenAPI document, CORS preflight from an unknown origin, the request log | No stack traces or SQL; metric labels are route templates; CORS answers no `Access-Control-Allow-Origin` for unknown origins |
| Event stream and WebSocket | A's stream while B uploads media; joining topics of B's records over the WebSocket | Only A's events; no module opens live topics in this build |
| Suspended tenant | Access token, API key, sign-in, public endpoints and MCP of a suspended tenant | All `403 tenant_suspended` |
| Guest flows | Public order lookup with a wrong token; anti-spam form token replay; comment on a draft or another tenant's entry | Refused or deduplicated |

### Findings

| ID | Severity | Area | Finding | Status |
| -- | -------- | ---- | ------- | ------ |
| P-1 | Medium | `auth` | An API key holding `auth.scim.manage` or `auth.oidc.manage` could create a SCIM token or add a sign-in provider. Both judge which accounts they may take over or link by the permissions of the person behind the key, not by the key's scope, so a narrow key could reach accounts with more rights than the key. | Fixed in #483: these actions need a signed-in session (`auth.session_required`), over REST and MCP |
| P-2 | Medium | `bookings` | The public endpoint that sends booking codes by SMS limited codes per phone number only; one client could ask codes for any number of phone numbers, each message paid by the shop. | Fixed in #487: at most 20 codes an hour per client address |
| P-3 | Low | kernel | Customer accounts could list the tenant's internal tags (`GET /api/v1/kernel/tags`), meant for staff. | Fixed in #489 |
| P-4 | Low | kernel | A domain claimed by one tenant and never verified blocked every other tenant from claiming it until the claim expired (7 days). | Fixed in #512: several tenants may wait on the same domain; the first to verify it gets it (a unique index on verified domains only), and the others' claims turn `failed` with the reason |
| P-5 | Low | `ledger`, `orders` | A buyer could choose any `http(s)` `return_url` for a payment, so the payment partner's page could send the buyer to an outside site after paying. | Fixed in #508: `return_url` must be an `https://` address on one of the tenant's verified domains, or on an origin the tenant lists in `ledger.payments.return_origins`; anything else is refused (`ledger.return_url_not_allowed`) |
| P-6 | Info | `auth` | A narrow API key can change its owner's display name, language and time zone (`PATCH /api/v1/auth/me`). | Accepted: no security setting is reachable; email, password, MFA and sessions need a session |

No finding let one tenant read or change another tenant's data, and none moved money.

### Not covered by the black-box test

- payment, bank-feed and carrier webhooks with real provider accounts (no outside service was called);
- passkeys, sign-in links, password reset and invitations end to end (they need a mail or browser);
- the tenant export, import and move archive formats;
- every MCP tool one by one (MCP was tested for authentication, key scope and a sample of tools).
